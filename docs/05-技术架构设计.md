## 1. 本文要回答的问题与结论

**问题：** 一个由 LLM 驱动的志愿填报系统，凭什么让人相信它的结论？

**简明答案：** 靠结构，不靠模型能力。我们把系统拆成「会犯错的组件」和「可验证的组件」两半，让前者只负责理解与表达，后者独占所有计算与判断；两者之间用强制的结构化契约连接，任何跨越契约的输出都必须带引用、可回填、可复算。这个约束在架构上体现为五层分层与三个横切面 `[已确定]`。

本节先给出三条全局结论，后续章节逐一展开论证。

1. **双轨结构。** LLM 与确定性程序不是主从关系，而是分工关系。LLM 负责理解、组织、解释；确定性程序负责位次计算、规则校验、组合优化、条件匹配 `[已确定]`。二者的接口是类型化的结果对象，不是自由文本。
2. **分层的目的不是整洁，是审计。** 五层中，「知识与数据层」与「可信数据源层」在物理上独立于「Agent 编排层」，任何进入 LLM 上下文的知识片段都必须携带来源标记（Provision / Lineage）。这样一次错误回答可以回溯到「是数据错」「是检索错」还是「是表达错」`[已确定]`。
3. **首要非功能目标是可审计，不是低延迟。** 在志愿填报场景里，一个说不清理由的正确结论与一个错误结论具有同样的破坏力——用户无法据此做出承担后果的决定 `[已确定]`。延迟目标服从于可审计目标，见 §6。

## 2. 设计原则

### 2.1 三条不可让渡的约束

这三条不是「最好满足」，而是「不满足则系统不成立」。它们决定了后面所有分层与选型。

| 约束 | 含义 | 违反后的具体后果 |
| --- | --- | --- |
| 可追溯 Traceability | 每个输出（画像结论、专业推荐、志愿方案）必须能回指到具体证据 Evidence 或具体数据行 | 用户无法判断该不该信；出现问题无法定责；画像纠错无法定位到源头 |
| 可校验 Verifiability | 凡影响录取判断的结论，必须由确定性规则引擎产出，LLM 只负责转述与解释 | 出现「看起来专业但算错了位次」的回答，且无法被自动检出 |
| 可拒绝 Refusability | 数据不足、规则冲突、来源不明时，系统必须输出「无法判断」并说明缺什么 | 系统会用流畅的语言填补空白，这正是幻觉最危险的形态 |

### 2.2 LLM 与确定性程序的分工

这是本项目的核心工程原则，也是可信度的主要论据。分工的判断标准只有一条：**该任务的正确性是否可以被机械验证**。可以被机械验证的，交给代码；不能被机械验证的，才交给 LLM，并附加约束。

| 任务 | 归属 | 理由 | 交给错误一方的后果 |
| --- | --- | --- | --- |
| 意图理解与会话路由 | LLM `[已确定]` | 自然语言表达千变万化，规则无法穷举 | 路由规则爆炸，「我想学生物但不想当医生」被误判为「专业查询」 |
| 澄清提问的措辞生成 | LLM `[已确定]` | 需要共情与语境适配，模板化会显得机械 | 对话体验崩塌，考生停止表达 |
| 证据片段摘要与要点抽取 | LLM `[已确定]` | 长文本语义压缩无确定算法 | 只能截断原文，用户读到一堆无关句子 |
| 画像条目草拟（结构化抽取） | LLM 生成 + 代码校验 schema `[设计中]` | 抽取需要语义理解；但字段合法性必须由代码判定 | 直接入库会污染画像，且无法统计字段缺失率 |
| 位次（Rank）换算与一分一段查询 | 代码 `[已确定]` | 纯数值查表与插值，可精确复算 | 差一位就可能跨越一个专业组，且用户无从发现 |
| 选科要求（Subject Requirements）匹配 | 代码 `[已确定]` | 布尔判定，规则明确 | 「物理必选、化学与生物二选一」这类复合条件，模型极易算错且言之凿凿 |
| 招生章程（Admission Charter）条件校验 | 代码 `[已确定]` | 单科成绩、体检结论、语种、加分项均为可判定条件 | 误报「可报」导致退档，是本项目最高等级事故 |
| 冲（Reach）稳（Match）保（Safety）组合优化 | 代码 `[已确定]` | 多目标约束求解，需要可复现 | 方案不可复现，用户换一个问题得到不同答案 |
| 招生计划可用性过滤 | 代码 `[已确定]` | 集合运算与年份省份批次一致性强校验 | 推荐一个当年不招生的专业，属于硬错误 |
| 引用回填与一致性检查 | 代码 `[已确定]` | 字符串级可判定 | 引用编号错位，等于没有引用 |
| 最终解释的措辞 | LLM，受模板与白名单约束 `[设计中]` | 需要把结构化结论转成可读中文 | 纯模板输出可读性差，用户读不下去 |

**关于灰色地带的处理。** 有一类任务既非纯语义也非纯数值，例如「判断某个专业的培养内容是否与考生的兴趣主题相关」。我们不把这类判断交给单一方，而是采用三段式：LLM 产出候选与理由 → 代码做字段级校验（必须落到具体课程或培养方案条目）→ Critic-Reviewer Agent 做反向检查（见文档 06）。这类任务的结论一律标为低置信度，且必须展示依据，不得作为志愿方案的主依据 `[设计中]`。

**为什么不让 LLM 做数值计算，即使它看起来会算。** 原因不是「它一定算错」，而是「它算错时你不会知道」。同一个位次计算请求，模型在不同上下文下可能给出不同数值，而两次输出都是同样流畅的中文。确定性程序的错误会抛异常、会被测试捕获、可以被复算；LLM 的错误只会被读起来更自信。在一个用户要据此填报志愿的场景里，这个差别是决定性的。

## 3. 分层架构

### 3.1 架构总图

```text
+-----------------------------------------------------------------------------+
|  接入层 Access Layer                                                        |
|  Web 端  |  移动 H5  |  高校招生后台  |  开放 API[规划]  |  对话记录导入通道    |
+----------------------+------------------------------+-----------------------+
                       |  统一会话信封 Session Envelope（身份/授权/场景/客户端）
                       v
+-----------------------------------------------------------------------------+
|  Agent 编排层 Orchestration Layer                                           |
|  Router  |  Planner  |  Orchestrator  |  Guardrail  |  Critic-Reviewer      |
|  Personal Agent ｜ Coach Agent ｜ Major Discovery Agent ｜ Admission Agent   |
|  Knowledge Retrieval Agent ｜ Decision Agent                                |
+----------------------+------------------------------+-----------------------+
                       |  工具调用 Tool Call            |  类型化结果 Typed Result
                       v                              v
+-----------------------------------------------------------------------------+
|  能力层 Capability Layer                                                    |
|  检索能力  |  规则校验能力  |  计算与优化能力  |  画像能力  |  解释生成能力     |
|  Hybrid Retrieval  |  Deterministic Rule Engine  |  多目标优化  |  证据管理     |
+----------------------+------------------------------+-----------------------+
                       |  只读数据访问                  |  只写证据与派生结果
                       v                              v
+-----------------------------------------------------------------------------+
|  知识与数据层 Knowledge & Data Layer                                        |
|  EKG 教育知识图谱  |  PKG 个人知识图谱  |  招生数据仓库  |  向量索引  |  画像库 |
+----------------------+------------------------------+-----------------------+
                       ^
                       |  带来源等级的批次导入 + 入库校验 + 冲突登记
+-----------------------------------------------------------------------------+
|  可信数据源层 Trusted Source Layer                                          |
|  省级考试院公开数据  |  高校招生章程与招生计划  |  高校培养方案  |  用户授权导入 |
+-----------------------------------------------------------------------------+

  横切面 Cross-cutting（贯穿全部五层，不属于任何一层）：
  ┌───────────────────────────────────────────────────────────────────────┐
  │ 可观测性 Observability ｜ 数据治理 Data Governance ｜ 安全与合规        │
  └───────────────────────────────────────────────────────────────────────┘
```

图中一个刻意的设计：**能力层向下的箭头是单向的**。知识与数据层不主动调用上层，所有跨层交互由能力层发起。这样「谁读了这个数据」的审计日志只需要在一个地方打点。

### 3.2 各层职责与禁止事项

分层的价值主要体现在「禁止」上。下表左列是允许，右列是不允许，后者比前者更能定义边界。

| 层 | 可以做什么 | 明确禁止 |
| --- | --- | --- |
| 接入层 | 身份与授权校验、会话生命周期、限流、多端协议适配 | 不解析业务语义；不直接访问知识与数据层 |
| Agent 编排层 | 意图路由、任务规划、工具编排、结果组装、拒答判定 | 不生成数值；不绕过工具直接拼装知识片段 |
| 能力层 | 提供可复用的原子能力，封装外部依赖与降级策略 | 不持有会话状态；不做跨能力的事务协调 |
| 知识与数据层 | 存储、索引、检索、版本管理、来源标注 | 不做业务判断；不产出面向用户的自然语言 |
| 可信数据源层 | 提供原始数据与来源元信息、采集时间、适用口径 | 不承担清洗逻辑（清洗属于数据治理横切面） |

### 3.3 模块边界与职责矩阵

| 模块 | 归属层 | 单一职责 | 输入 → 输出 | 不负责 |
| --- | --- | --- | --- | --- |
| Personal Memory | 知识与数据层 + 能力层 | 长期交互记忆（Long-term Interaction Memory）的存储、检索与衰减 | 会话事件 → 结构化记忆条目 | 不做画像判断，画像判断属于画像能力 |
| Self Discovery | Agent 编排层 | 主持自我探索（Self Discovery）对话，驱动工作观／人生观（Workview／Lifeview）与美好时光日志（Good Time Journal）产出 | 考生表达 → 证据 + 待验证假设 | 不做专业推荐；不计算录取概率 |
| Major Discovery | Agent 编排层 | 把画像线索与 EKG 结合，产出专业探索假设 | 画像快照 + 检索结果 → 专业候选与理由 | 不做志愿组合；不判断录取可行性 |
| University Agent | Agent 编排层 | 面向考生的高校知识问答与专业解释 | 问题 → 带引用的回答 | 不得代表校方发言 |
| Admission Agent | Agent 编排层 | 面向高校的招生知识库问答与咨询分析 | 高校侧问题 → 带引用的回答 + 咨询统计 | 不得接触未经授权的考生画像 |
| Decision Engine | 能力层 | 志愿方案生成：冲稳保组合、约束求解、可复现输出 | 考生约束 + 候选专业 → 方案与逐条依据 | 不生成叙述性文案段落结构 |
| Knowledge Graph | 知识与数据层 | EKG 与 PKG 的建模、对齐、版本演进 | 实体关系变更 → 图谱版本 | 不做检索排序 |
| Data Governance | 横切面 | 来源分级、授权、脱敏、审计、质量校验 | 数据批次 → 合规数据 + 质量报告 | 不做业务规则判断 |

**四处最容易混淆的边界，需要单独说清：**

其一，**Personal Memory 与个人画像（Personal Profile）不是一回事。** 记忆是「原材料仓库」，画像是对原材料做出的、带置信度的判断结论。记忆条目可以原样展示给用户（这是一段对话），画像条目必须带置信度与依据（这是一个判断）。把两者合成一个模块会让「删除一条证据」和「撤销一个结论」混为一谈，而文档 08 要求这两件事都独立可执行。二者共用存储层，但写入路径与生命周期不同 `[设计中]`。

其二，**Major Discovery 与 Decision Engine 的界线是「可能性」与「可行性」。** 前者回答「这个方向值不值得了解」，允许发散、允许低置信度；后者回答「这个方案能不能填」，必须收敛、必须每条可复算。二者的输出格式因此也不同：前者是假设列表，后者是带约束满足状态的方案。

其三，**University Agent 与 Admission Agent 共用知识库但不共用会话。** 它们在数据上同源（同一份高校招生知识），在编排上完全隔离，因为一侧面向考生、一侧面向高校招生办，两侧的信息披露边界不同。任何跨侧数据流动都必须经过考生主动授权，这一点由文档 08 约束，架构上体现为两个 Agent 不共享会话上下文存储。

其四，**Knowledge Graph 负责「是什么」，Data Governance 负责「能不能用」。** 一条录取记录在 EKG 里存在，不等于它可以被展示——可能来源等级过低，或已过适用年份。架构上要求 EKG 的每次读取都返回来源等级与口径字段，由上层决定是否可用，而不是在入库时就删掉低等级数据。

## 4. 一次「专业探索」请求的完整数据流

下面用一条输入串起全部五层。输入是：**「我想做和生物有关的事，但不想当医生」**。链路中出现的专业名、画像条目与数值**均为示例，非真实数据**，仅用于说明调用顺序与依赖关系。

### 4.1 链路总览

```text
考生输入（自然语言）
      │
      ▼
[1] 接入层：构造 Session Envelope
      │     身份 / 授权范围 / 场景标签 / 客户端能力 / 请求 ID
      ▼
[2] Router：意图判定 → major_exploration（置信度：中）
      │     低置信度时进入澄清分支，不猜测
      ▼
[3] Personal Agent：只读画像快照 + 近 30 天情景摘要
      │     ├─ 命中画像条目：对「生命科学」类主题有 3 条中等置信度证据
      │     └─ 命中冲突：1 条证据显示对解剖类内容不适
      ▼
[4] 并行扇出 ────────────────────────────────────────────┐
      │  A) Coach Agent：生成 1 个非引导性澄清问题            │
      │  B) Knowledge Retrieval Agent：启动混合检索            │
      ▼                                                      │
[5] 混合检索：结构化过滤 → 关键词 → 向量 → 重排 → Top-K      │
      │     过滤条件：学科门类含理学/工学/农学/医学；排除临床医学类
      ▼                                                      │
[6] Major Discovery Agent：组织为 3 组专业假设，逐条挂证据    │
      │     每组含：专业名 / 相关课程 / 与画像的对应点 / 反证   │
      ▼                                                      │
[7] 确定性校验闸门（Deterministic Rule Engine）              │
      │     选科要求匹配 / 数据年份省份一致性 / 招生计划可用性   │
      │     未通过项直接剔除，不交给 LLM「再想想」              │
      ▼                                                      │
[8] Critic-Reviewer Agent：反向审核                            │
      │     检查：每个断言是否可回填引用 / 是否超出证据范围      │
      │     不通过 → 打回 [6] 重写（最多 1 次），仍不过则降级    │
      ▼                                                      │
[9] 解释生成：模板骨架 + LLM 措辞，逐句挂引用编号              │
      │
      ▼
[10] 写回：情景记忆（本轮摘要，自动）+ 画像候选条目（待确认，不自动生效）
      │
      ▼
输出：带引用的专业探索结果 + 1 个澄清问题 + 明确的「下一步可以做什么」
```

### 4.2 分步说明与失败降级

每一步都必须定义失败时的行为。**没有降级策略的步骤等于没有设计。**

| 步骤 | 组件 | 关键输出 | 失败时的降级 |
| --- | --- | --- | --- |
| 1 | 接入层 | 会话信封 | 授权字段缺失 → 直接拒绝，不进入后续链路 |
| 2 | Router | 意图标签 + 置信度 | 置信度低 → 只出澄清问题，不预生成推荐 |
| 3 | Personal Agent | 画像快照 | 画像为空 → 转 Self Discovery 冷启动流程，本次不做专业推荐 |
| 4 | Coach Agent | 1 个澄清问题 | 生成失败 → 出预设的通用问题，不影响主链路 |
| 5 | Hybrid Retrieval | Top-K 片段 + 来源等级 | 向量索引不可用 → 降级为关键词 + 结构化过滤，并在结果上标注「检索能力降级」 |
| 6 | Major Discovery Agent | 专业假设列表 | 无足够证据 → 输出「不足以形成假设」，给出补证据的建议路径 |
| 7 | Rule Engine | 通过／剔除／原因码 | 规则库缺该省份数据 → 该专业标为「无法校验」，不进入推荐主列表 |
| 8 | Critic-Reviewer | 通过／打回／降级 | 审核不可用 → 强制降低输出置信度档位，并在正文提示「未经过独立审核」 |
| 9 | 解释生成 | 带引用的中文段落 | 引用回填失败 → 该句删除，不删整段（保信息密度，去不可信断言） |
| 10 | 写回 | 记忆与画像候选 | 写入失败 → 记入补偿队列，不阻塞用户可见结果 |

这里有一个反直觉的取舍：**第 9 步引用回填失败时删句而不删段。** 整段删掉会让用户拿不到有用的中间信息；只删回填失败的句子，可以在保住信息量的同时把「不可信断言」清干净。代价是段落可能读起来不连贯，我们接受这一点，并在中文措辞上留了衔接模板 `[设计中]`。

## 5. 技术选型：候选、判据、取舍

本节不给出唯一答案。每项选型给出 2–3 个候选、判定依据、以及当前倾向与为什么倾向。所有倾向都标注为 `[设计中]` 或 `[假设]`，最终结论留待文档 11 的 MVP 实测决定。**任何一项选型在没有实测数据之前都不应被写成既成事实。**

### 5.1 Agent 编排框架

| 候选 | 优势 | 代价 |
| --- | --- | --- |
| A. 通用 Agent 框架（现成 ReAct／图编排） | 上手快，社区生态成熟，多 Agent 支持开箱可用 | 执行路径不确定，难以强制「必须走规则闸门」；调试黑盒 |
| B. 自研轻量编排（显式状态机 + 工具注册表） | 路径可控、可审计、可断言；每一步可插桩 | 开发量大，多 Agent 协作需自己实现；追踪能力要自建 |
| C. 工作流引擎（DAG 编排 + LLM 节点） | 确定性路径天然可审计，重试与超时成熟 | 难以表达探索性对话；DAG 僵硬，回退到上一节点代价高 |

**判据（按权重排序）：** ① 能否强制插入确定性校验闸门并保证不被跳过；② 每一步是否可完整回放以支持审计；③ 多 Agent 并行与打回（Critic 打回重写）是否原生支持；④ 团队规模能否维护。

**当前倾向：B 为主、C 为骨架的混合方案 `[假设]`。** 对话型链路（自我探索、澄清）用显式状态机保持可控，数据计算型链路（志愿方案生成）用 DAG 保证可复现。放弃 A 的主要原因是它在「保证 LLM 不能绕过规则校验」这一点上无法给出结构性保障，只能靠提示词祈祷。**验证方式：** 在 Phase 1 MVP 中用 20 条固定脚本回放，统计「规则闸门被绕过」的次数，要求为 0。

### 5.2 检索方案

| 候选 | 优势 | 代价 |
| --- | --- | --- |
| A. 纯向量检索 | 语义泛化强，「想学生物但不当医生」这类模糊表达命中好 | 专业名称近义混淆严重；不可解释；无法表达硬过滤 |
| B. 纯关键词（BM25 类） | 专业名词精确命中；可解释；无需嵌入成本 | 无法处理自然语言描述；同义改写全失 |
| C. 结构化过滤 + 关键词 + 向量 + 重排的混合检索 | 三者互补，硬约束先行可把召回空间压到可控 | 链路长，每段都可能失败；需要设计四段降级 |

**判据：** ① 「生物医学工程」与「生物工程」这类名称相似但培养内容差异极大的专业能否被区分；② 选科要求这类硬约束能否作为前置过滤而非事后判断；③ 每个召回结果能否解释「为什么被召回」。

**当前倾向：C，且结构化过滤必须前置 `[设计中]`。** 理由很实际：志愿场景里的错误召回代价很高，把一个要求「物理 + 化学」的专业推荐给没选化学的考生，是硬错误而非体验问题。前置过滤把这个错误在召回阶段就消除掉，比事后校验更可靠。放弃纯向量的原因是它无法表达「必须满足」这种语义。详见文档 07 §7 的降级设计。

### 5.3 数据存储

| 候选 | 优势 | 代价 |
| --- | --- | --- |
| A. 关系库 + 独立图库（双写） | 关系库保证强一致与事务；图库擅长多跳关系遍历 | 双写一致性需自行保证；运维两套系统 |
| B. 单库多模（关系库带 JSON／图扩展） | 一套系统，事务简单，运维轻 | 多跳查询性能受限；图语义表达不完整 |
| C. 文档库 + 图库 | 半结构化数据（培养方案、章程原文）存储灵活 | 结构化查询能力弱，统计类需求吃力 |

**判据：** ① 招生计划、录取记录这类强结构化数据是否需要事务与唯一约束；② 兴趣主题到学科知识点到专业培养要求的映射是否需要多跳遍历；③ Phase 1 的团队能否承担两套存储的运维。

**当前倾向：A，但图中的边先落在关系库的邻接表上，Phase 2 再引入独立图库 `[规划]`。** 这是一个明确的成本取舍：我们在 Phase 1 放弃图库的遍历性能，换取运维简单与数据一致性；如果 MVP 阶段发现「兴趣到专业的映射」查询深度超过 3 跳且成为瓶颈，再迁移。**触发迁移的信号：** 单次对齐查询的 P95 超过 800 ms（见 §6）。

### 5.4 确定性规则引擎

| 候选 | 优势 | 代价 |
| --- | --- | --- |
| A. 手写代码实现校验函数 | 最直接，性能好，调试简单 | 招生章程逐年变化，改一处要发版；规则与代码耦合，无法给招生办看 |
| B. 声明式规则 DSL（条件表达式 + 原因码） | 规则可读可审，可交给非工程角色复核；变更不需发版 | 需要设计 DSL 与执行器；表达力有上限，复杂条件仍要落回代码 |
| C. 商业规则引擎（BRMS） | 功能完整，有可视化编辑与审计 | 引入外部依赖与成本；与现有技术栈集成成本高 |

**判据：** ① 招生章程变更后，从「发现变化」到「规则生效」的周期；② 规则能否被招生办人员读懂并复核（这是可信度的关键一环）；③ 每条规则失败时能否给出可读的原因码。

**当前倾向：B，复杂条件用 B 调 A 的方式 `[设计中]`。** 关键论据是第 ② 条：如果招生办无法复核规则，那么「规则校验」在合作方眼里就只是另一个黑盒。放弃 C 是因为在本项目规模下，引入 BRMS 的集成与学习成本高于收益，而这个结论在高校侧接入数量显著增长后可能反转 `[假设]`。

### 5.5 嵌入模型与长上下文

| 候选 | 优势 | 代价 |
| --- | --- | --- |
| A. 通用中文嵌入模型 | 成本低，开箱可用 | 教育领域术语（专业组、位次、选科）区分度不足 |
| B. 领域微调嵌入 | 教育术语区分度显著提升 | 需要标注数据与训练成本；过拟合风险 |
| C. 长上下文直接投喂（不做检索） | 省掉检索链路，上下文完整 | 成本随会话线性增长；无法给引用定位；超长后精度下降 |

**判据：** ① 专业名称近义项的区分准确率；② 单次对话成本是否可接受；③ 能否为每句话给出可回填的引用位置。

**当前倾向：A 起步，B 待评测后决定，明确放弃 C `[设计中]`。** 放弃 C 的理由是硬性的：长上下文无法为具体句子提供精确的引用定位，而我们要求引用必须能回填到具体数据行（§2.1）。这是一个用成本换可审计性的选择，与文档 01 的设计哲学一致。**验证方式：** 构造 100 组近义专业名称对照集，测 A 与 B 的 Top-1 区分准确率。

### 5.6 可观测性

候选包括：A. 仅结构化日志；B. 结构化日志 + 分布式链路追踪；C. 在 B 之上增加「决策快照」（每轮对话把当时的画像快照、检索结果、规则判定结果整体持久化）。

**当前倾向：C `[已确定]`。** 决策快照是本文最看重的一项工程投入。理由：用户投诉「你上次不是这么说的」时，普通日志只能证明系统说过什么，决策快照能证明**系统当时依据什么这么说**。后者才是可审计。代价是存储成本上升，我们接受，因为对话轮次规模在早期阶段可控。

## 6. 非功能需求目标

以下全部是**目标值**，不是承诺值，也不是已达成的指标。每一项都给出可验证的口径，避免出现「响应很快」这类不可检验的表述。

| 维度 | 目标值 | 口径 | 验证方式 |
| --- | --- | --- | --- |
| 首字延迟 | P95 < 2.5 s | 单轮对话，从提交到首 token 返回 | 线上采样 + 回放压测 |
| 完整响应延迟 | P95 < 8 s | 专业探索类请求，含检索与校验 | 同上 |
| 引用可回填率 | 100% | 输出中含事实断言的句子，其引用必须能定位到数据行 | 自动化脚本逐句校验 |
| 规则校验覆盖率 | 100% | 凡涉及录取可行性的断言，必须存在对应规则判定记录 | 决策快照审计，缺记录即视为未覆盖 |
| 可用性 | 99.5%（Phase 2 目标） | 自然月，不含计划内维护 | 监控统计 |
| 单会话成本 | 目标区间随阶段调整 `[假设]` | 单次会话 token 与检索调用折算成本 | 账单归集到 session_id |
| 可观测性覆盖 | 链路追踪 100% 采样（Phase 1） | 关闭采样，全量记录 | 追踪后端统计 |

**为什么把「引用可回填率」和「规则校验覆盖率」设为 100% 而不是 99%。** 因为这两项一旦允许失败率，失败就会集中在最复杂的专业与最边缘的省份——恰恰是最需要准确的地方。宁可让系统拒答，也不能让这两项打折。这条原则与文档 06 的拒答策略直接对应。

## 7. 横切关注点

### 7.1 安全与合规

数据分类分级、授权模型、脱敏与审计的具体规则由 [数据治理隐私与合规](08-数据治理隐私与合规.md) 定义。架构上只约定三件事：第一，接入层是唯一做身份与授权判定的地方，下游组件信任会话信封而不重复判定；第二，任何跨侧数据流动（考生画像进入高校侧）必须携带授权令牌，令牌至少包含**授权 ID、场景、期限、字段集**四项，由接入层统一校验，过期即失效且不提供自动续期（字段语义与白名单以[文档 08 §6](08-数据治理隐私与合规.md#6-高校侧使用考生画像的硬边界) 为准）；第三，审计日志只记录「谁在什么授权下访问了什么」，不记录不必要的原文。

### 7.2 可观测性三件套

结构化日志记录事件；链路追踪记录跨组件调用；决策快照记录当轮判断依据。三者的关联键统一为 `request_id` 与会话 `session_id`。缺任何一件，「为什么系统这么答」都会变成推测。

### 7.3 成本控制

分三层：第一层缓存，知识检索结果按「查询指纹 + 数据版本」缓存，数据版本变更即失效；第二层模型分级，路由与抽取用小模型，解释生成用大模型，这一步需要在文档 06 的评测里验证降级后质量可接受；第三层请求合并，同一轮内的多次检索合并为一次批查询。**取舍：** 缓存会带来「数据更新后短暂不一致」的风险，我们用数据版本号做强制失效，宁可缓存命中率低也不接受陈旧数据进入解释生成。

## 8. 当前未解决的架构难题

本节单列，是因为这些问题的存在本身就是架构文档的一部分。假装它们不存在，比写错更糟。

1. **画像到专业的映射缺乏基准真值（no ground truth）。** 「这个考生适不适合学这个专业」没有可观测的正确答案，只有多年后的回溯。当前做法是用「专家一致性 + 用户认可度」双指标近似，但两者都可能系统性偏离。**必须重设计的信号：** 若 MVP 中专家与用户的判断分歧率持续高于阈值，则说明当前的对齐机制（见文档 07 §4）不成立，需要引入纵向追踪。
2. **规则引擎表达力与招生章程自然语言的落差。** 招生章程里存在大量「原则上」「视情况」「同等条件下优先」这类非判定性表述。当前把它归入「不可校验」，由系统明确告知用户「此条需人工确认」。这条路径的问题是：如果不可校验条款占比过高，规则校验的价值被稀释。**待测：** 在试点省份抽样统计不可校验条款的比例。
3. **多省份数据的异构性。** 批次名称、科类划分、专业组规则、加分政策在各省不同，同一套 schema 难以无损承载。当前倾向是「核心表 + 省份扩展字段」，但这会让校验规则也省份化，维护成本上升。这是 `[研究]` 状态的问题。
4. **长会话中的记忆衰减与矛盾证据。** 用户三个月前说想学医，昨天说不想。系统需要知道哪条更可信，而「时间近 = 更可信」的简单规则会丢掉真实的长期兴趣（这正是 RQ1 要研究的问题）。当前不做自动覆盖，而是保留矛盾并把冲突显式呈现给用户。
5. **流式输出与引用回填的时序矛盾。** 用户希望边想边出字，但引用回填要求句子在展示前完成校验。当前方案是「先出骨架、后补引用」，代价是用户可能先读到一句随后被删掉的话。**这是一个尚未解决的体验—可信度权衡点。**
6. **多 Agent 审核的成本与延迟。** Critic-Reviewer 的双向审核会显著拉长链路。当前只在「涉及录取判断」的输出上强制启用，其余场景抽样启用。这个划分是否合理，需要在文档 11 中验证。
7. **两侧数据隔离下的联合检索。** 高校侧希望知道「考生关心什么」，考生侧要求画像不外流。聚合统计（只出分布不出个体）在 k-匿名阈值选择上没有确定答案，阈值太低有重识别风险，太高则统计无意义。交由文档 08 与后续研究裁决。
