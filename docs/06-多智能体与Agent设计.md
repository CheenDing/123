## 1. 设计立场

**问题：** 多 Agent 是不是把一个问题拆成七个 Agent 就叫架构？

**简明答案：** 不是。本文坚持三条立场，它们直接决定了后面为什么不设更多角色。

第一条，**Agent 的划分依据是「职责与权限边界」，不是「话题」。** 每增加一个 Agent，就增加一次 LLM 调用的不确定性和一份延迟成本。所以只有当两个职责的**权限不同**（能读什么、能写什么、能对外发什么）时，才拆成两个 Agent。权限相同的职责合并，用工具区分。

第二条，**编排要能被审计，所以主链路必须是显式的。** 不允许「让 Agent 自己决定调用谁」的自由漫游。Router 做一次路由，Orchestrator 按预设路径推进，Critic-Reviewer 做拦截。自由度过高会让第 5 节的记忆写入和第 7 节的幻觉控制都失去确定性。

第三条，**Agent 之间不通过自然语言传递事实，只通过类型化结果传递。** 一个 Agent 说「我觉得这个专业挺合适」传给下一个 Agent，等于把幻觉洗了一遍继续用。传递的东西必须是 `{major_id, support_evidence_ids, confidence_tier, rule_check_status}` 这样的结构。这条对齐文档 05 §2.2 的分工原则。

**我们放弃了什么：** 放弃了「涌现式多 Agent 协作」带来的灵活性。代价是复杂查询的路径可能不是最优，好处是任何一条输出都能被完整回放和定责。在志愿填报这个用户要据此承担后果的场景里，我们选择后者。

## 2. Agent 角色清单

### 2.1 角色总表

七个角色 `[设计中]`。下表最后两列是划分的真正依据——权限差异。

| 角色 | 面向 | 核心职责 | 可写数据 | 可对外请求 |
| --- | --- | --- | --- | --- |
| Personal Agent | 考生 | 会话总入口、意图承接、跨模块串联、结果组装 | 情景记忆、画像候选 | 否 |
| Coach Agent | 考生 | 主持自我探索对话，用苏格拉底式提问产出证据 | 情景记忆、画像候选 | 否 |
| Major Discovery Agent | 考生 | 结合画像与 EKG 产出专业假设与解释材料 | 情景记忆 | 否 |
| Knowledge Retrieval Agent | 内部 | 唯一允许访问 EKG 与招生数据的角色，负责检索与降级 | 无 | 否 |
| Decision Agent | 考生 | 生成冲（Reach）、稳（Match）、保（Safety）方案，调用规则与优化能力 | 无（方案不落库，除非用户保存） | 否 |
| Admission Agent | 高校 | 招生知识库问答、咨询分析 | 高校侧会话日志 | 否 |
| Critic-Reviewer Agent | 内部 | 反向审核其他角色的输出，可打回 | 无 | 否 |

**称谓约定（避免与文档 05 混淆）：** 上表的 `Admission Agent` 指**面向招生办内部**的角色。考生在高校侧对话时接触到的「官方招生 Agent」，在架构上是文档 05 的 **University Agent**（面向考生的高校官方知识与专业解释入口），由本表的 Admission Agent 共享知识源、但会话完全隔离。两词不可互换：`University Agent` 是对外服务面，`Admission Agent` 是对内工作台面。术语登记见[文档 14 §2](14-附录B-写作与引用规范.md#2-术语统一表强制)。

**为什么没有「招生政策解读 Agent」「院校对比 Agent」「性格标签 Agent」。** 前者与 Admission Agent 权限相同、只是话题不同，合并为工具；中者是 Major Discovery Agent 的一种输出形式；后者违反文档 01 的设计哲学（不给考生贴人格标签），根本不应存在。

### 2.2 各角色的职责与非职责

**Personal Agent `[设计中]`。** 它是考生侧唯一对外的会话主体，负责把用户的一句话变成一次编排任务，再把结果组装成一段可读回答。它**不生成事实性内容**，所有事实来自工具返回。它持有当前会话的工作记忆，并在会话结束时把摘要交给 Personal Memory。非职责：不做检索、不做计算、不做规则判断。

**Coach Agent `[设计中]`。** 只做一件事：通过提问帮助考生把自己的兴趣、能力线索、价值观说清楚，并把每次表达沉淀为带定位的证据。它的输出不是结论而是**问题与证据**。非职责：不做专业推荐。这一点必须硬隔离——一旦 Coach 开始推荐专业，提问就会变成引导，画像立刻被污染（见 §6.2）。

**Major Discovery Agent `[设计中]`。** 把画像线索与 EKG 检索结果对齐，产出 2–4 组专业假设，每组必须包含：相关专业、支撑课程或培养方案条目、与画像的对应关系、以及**至少一条反证或不确定点**。强制要求反证是这个角色的设计要点，它让输出天然带着自我怀疑，而不是一味论证。

**Knowledge Retrieval Agent `[设计中]`。** 系统内唯一允许访问 EKG 与招生数据仓库的角色。所有检索请求经它代理，好处是检索策略、降级逻辑、来源等级标注只在一处实现，也只在审计里出现在一处。非职责：不做相关性判断之外的推理，不生成自然语言解释。

**Decision Agent `[设计中]`。** 接收考生约束（省份、年份、科类或选科、位次、地域偏好、专业偏好、风险偏好），调用确定性规则引擎与多目标优化能力，产出冲（Reach）稳（Match）保（Safety）分档方案。它的核心纪律是：**自己不产生任何数值**，所有位次、概率、约束满足状态全部来自工具。非职责：不做专业解释，解释归 Major Discovery Agent。

**Admission Agent `[设计中]`。** 面向高校招生办，基于高校自有招生知识库回答问题，并输出咨询热点分析。硬约束：不得代表校方做承诺性表述；不得访问未经考生授权的画像数据。它与 University Agent 共用知识源但完全隔离会话（见 [技术架构设计](05-技术架构设计.md#33-模块边界与职责矩阵) 中关于模块边界的说明）。

**Critic-Reviewer Agent `[已确定]`。** 唯一职责是**反向**审核：给定一份待发布的输出与它声称的依据，检查每一句事实断言是否真有对应引用、引用是否支持该断言、是否有超出证据范围的推断。它不写内容，只判定通过、打回或降级。设置它的理由很直接：生成者天生倾向自证，让同一个角色自我审查的检出率极低。

## 3. 编排模式

五种模式，各有其适用场景与不适用场景。**用错模式比不用模式更糟**，例如在需要确定性的链路上用反思模式，会让同一输入产生不同输出。

| 模式 | 适用场景 | 不适用场景 | 成本 |
| --- | --- | --- | --- |
| 路由 Routing | 入口意图分流（探索／查询／决策／导入） | 意图本身模糊且需多轮澄清 | 低（1 次调用） |
| 串行 Sequential | 有严格依赖的链路（检索 → 校验 → 生成） | 各步骤可并行时（浪费延迟） | 中 |
| 并行 Parallel | 相互独立的取证（澄清问题生成 + 检索） | 后一步依赖前一步结果 | 中（可降延迟） |
| 反思 Reflection | 措辞质量、解释可读性优化 | 数值与规则判断（不可靠） | 高（≥2 次调用） |
| 多 Agent 审核 Review | 涉及录取判断的输出发布前 | 纯事实查询（过度设计） | 高（+1 次调用） |

### 3.1 主链路编排图

```text
                     考生输入
                        │
                        ▼
              ┌──────────────────┐
              │  Router（路由）   │  意图标签 + 置信度
              └────────┬─────────┘
                       │  置信度低 → 只出澄清问题，不进主链路
        ┌──────────────┼──────────────┬──────────────┐
        ▼              ▼              ▼              ▼
   major_explore   self_discover   admission_q    decision
        │              │              │              │
        ▼              ▼              ▼              ▼
  ┌───────────────────────────────────────────────────────┐
  │  Orchestrator（串行主链 + 并行取证）                    │
  │                                                       │
  │   [并行扇出]                                          │
  │    ├── Coach Agent ──→ 1 个澄清问题                   │
  │    └── Knowledge Retrieval Agent ──→ Top-K + 来源等级  │
  │              │                                        │
  │              ▼                                        │
  │    Major Discovery Agent ──→ 专业假设 + 反证            │
  │              │                                        │
  │              ▼                                        │
  │    【确定性校验闸门】Rule Engine（不可跳过）             │
  │              │                                        │
  │              ▼                                        │
  │    Critic-Reviewer Agent ──→ 通过／打回／降级           │
  │              │  打回时：回退到 Major Discovery（最多 1 次）│
  │              ▼                                        │
  │    解释生成（模板骨架 + LLM 措辞 + 引用回填）            │
  └───────────────────────┬───────────────────────────────┘
                          ▼
              结果组装 + 记忆写回 + 画像候选
```

图中「确定性校验闸门」被画成主链上的方块而非可选项，是刻意的：它在实现上是一个**必须被调用的拦截器**，Orchestrator 若未调用它，输出会被下游拒绝组装 `[设计中]`。

### 3.2 打回机制的具体规则

Critic-Reviewer 打回不能无限循环。规则如下 `[设计中]`：

第一，每个输出最多被打回 1 次。第二次仍不通过则进入降级路径，而不是继续重试。

第二，降级路径是**降低置信度档位 + 显式告知**，例如「以下内容未经独立审核，请谨慎参考」。不静默发布，也不整段丢弃。

第三，打回必须带**具体原因码**（如 `CITATION_MISSING`、`CLAIM_EXCEEDS_EVIDENCE`、`RULE_STATUS_ABSENT`），而不是「再写一遍」。没有原因码的打回等于重新掷骰子。

## 4. 工具与 Skills 设计

### 4.1 副作用分级

工具按副作用分三级。分级的意义在于：**只有一级工具可以被 Agent 自由调用，二三级必须经过编排层的显式授权。**

| 级别 | 定义 | 工具示例 | 调用约束 |
| --- | --- | --- | --- |
| L1 只读 Read-only | 不改变任何持久状态 | `search_ekg`、`get_curriculum`、`query_admission_plan`、`compute_rank`、`validate_subject_requirements`、`validate_charter_rules`、`optimize_rms` | 可自由调用，全部记录审计 |
| L2 写画像 Write-profile | 改变用户长期数据 | `read_profile`、`write_evidence`、`propose_profile_entry`、`confirm_profile_entry`、`delete_evidence` | `propose_*` 只产生候选，用户确认后 `confirm_*` 才生效；`delete_*` 必须用户发起 |
| L3 外部请求 External | 跨越信任边界 | `request_university_match`（向高校侧发起个性化匹配请求）、`import_chat_history`（导入第三方 AI 对话）、`export_profile`（导出个人数据） | 必须持有效授权令牌，且令牌含场景与期限；每次调用需在 UI 显式呈现 |

### 4.2 工具清单

| 工具 | 级别 | 输入要点 | 输出要点 | 主要调用方 |
| --- | --- | --- | --- | --- |
| `search_ekg` | L1 | 查询意图、结构化过滤条件、Top-K | 片段 + 来源等级 + 数据版本 | Knowledge Retrieval Agent |
| `get_curriculum` | L1 | 专业标识、年份 | 培养方案条目、课程列表、学分结构 | Knowledge Retrieval Agent |
| `query_admission_plan` | L1 | 省份、年份、科类或选科、批次 | 计划数、专业组、选科要求 | Decision Agent |
| `compute_rank` | L1 | 省份、年份、分数、科类 | 位次（Rank）+ 换算口径 | Decision Agent |
| `validate_subject_requirements` | L1 | 选科组合、专业组要求 | 通过／不通过 + 原因码 | Decision Agent |
| `validate_charter_rules` | L1 | 考生条件（单科成绩、体检、语种、加分）、章程条款 | 逐条判定 + 不可校验条款清单 | Decision Agent |
| `optimize_rms` | L1 | 候选专业集、约束、风险偏好 | 冲稳保分档方案 + 每项约束满足状态 | Decision Agent |
| `read_profile` | L2 | 考生标识、需要的条目类型 | 画像条目快照（含置信度与证据） | Personal／Coach／Major Discovery |
| `write_evidence` | L2 | 证据原文、定位、时间 | 证据标识 | Coach Agent |
| `propose_profile_entry` | L2 | 条目类型、内容、关联证据、置信度 | 候选条目（不生效） | Coach／Major Discovery |
| `confirm_profile_entry` | L2 | 候选标识、用户确认 | 生效条目 | Personal Agent（代用户操作） |
| `delete_evidence` | L2 | 证据标识、用户发起的删除请求 | 删除结果 + 受影响条目 | Personal Agent |
| `request_university_match` | L3 | 授权令牌、匹配范围 | 高校侧返回结果（不含原始画像） | Personal Agent |
| `import_chat_history` | L3 | 用户授权、文件、留存期限 | 解析后的证据候选 + 处理范围说明 | Personal Agent |
| `export_profile` | L3 | 授权、导出格式 | 完整画像与证据包 | Personal Agent |

### 4.3 Skills 的组织方式

Skill 是「一组工具 + 一段固定策略」的封装，不是提示词模板 `[规划]`。当前规划三个 Skill：`self_discovery_cycle`（一次完整的自我探索循环，含开场、提问、证据沉淀、小结）、`major_exploration`（一次专业探索，含检索、假设生成、校验、解释）、`application_plan`（一次志愿方案生成，含约束收集、规则校验、组合优化、方案呈现）。

把策略封装进 Skill 而不是写进每个 Agent 的提示词，原因是**可评测**：Skill 是评测的最小单位，同一 Skill 换模型、换提示词可以直接对跑指标（见 §8）。

## 5. 记忆设计

### 5.1 四层记忆

四层不是四个数据库，而是四种**生命周期与用途不同**的记忆。混淆它们会导致「用户想删掉一句话，结果整个画像没了」这类问题。

| 层 | 名称 | 内容 | 生命周期 | 可被用户直接看到 |
| --- | --- | --- | --- | --- |
| L1 | 工作记忆 Working Memory | 当前会话的上下文、临时变量、已调用工具结果 | 单次会话，结束即释放 | 部分（对话记录） |
| L2 | 情景记忆 Episodic Memory | 「什么时候发生了什么」：会话摘要、关键表达、任务记录 | 长期，可衰减 | 是 |
| L3 | 语义记忆 Semantic Memory | 从多次情景中归纳出的稳定认知，如「对生命科学的兴趣持续 3 个月以上」 | 长期，需反复验证 | 是（以画像形式） |
| L4 | 个人画像 Personal Profile | 结构化判断结论：兴趣主题、能力线索、价值观、待验证假设 | 长期，带置信度 | 是，可纠正可删除 |

L2 与 L3 的区别容易被忽视：L2 是「事件」，L3 是「从事件归纳出的规律」。L2 可以原样展示，L3 必须标注它依据了哪些 L2 条目。这条区分对应文档 08 中「删除证据」与「撤销结论」两个独立操作。

### 5.2 写入策略

写入分三类，路径不同 `[设计中]`：

**自动写入（无需用户确认）：** 会话摘要进 L2。这是记录，不是判断，风险低。写入时附带 `session_id`、时间、涉及模块。

**候选写入（需用户确认才进 L4）：** Agent 从对话中抽出的画像条目。流程是 `propose_profile_entry` → 用户在界面上看到「我观察到你可能……依据是这段话，对吗？」→ 确认或否认。**未经确认的候选不参与后续推荐**，只在画像页以「待确认」状态展示。这条是硬约束，理由见 §6.2：不确认就生效会让引导性提问的污染直接进入画像。

**归纳写入（需多次证据才进 L3）：** 单次表达不构成稳定认知。当前设计是同一主题至少出现 3 次独立证据、且跨 14 天以上，才生成 L3 归纳 `[假设]`。这两个阈值是拍的，需要文档 09 的纵向数据校准。

### 5.3 遗忘策略

不做全量永久保留。三类遗忘 `[设计中]`：

第一，**权重衰减。** L2 条目随时间降低检索权重，但不删除。半年未再出现的兴趣主题，权重降到不参与主动推荐，但仍可被用户主动查回。

第二，**验证淘汰。** L3 归纳如果连续两次被新证据反驳，降级回待验证状态，而不是直接删除——因为「曾经这样认为」本身是有信息量的。

第三，**用户主动删除。** 用户删除一条证据后，所有依赖它的 L3 与 L4 条目必须重算或降级。这是文档 08 的合规要求，在架构上意味着**画像条目必须记录依赖的证据标识集合**，否则删除无法传播。

### 5.4 冲突消解

冲突有三种，处理方式不同。

**时间冲突**（「三个月前说想学医，昨天说不想」）：不自动用新证据覆盖旧证据。保留两者，把冲突显式呈现给用户，由用户裁定。理由：时间近不等于更真实，长期兴趣的反复恰恰是 RQ1 要研究的信号。

**来源冲突**（用户自述「我数学很好」vs 成绩单显示数学偏弱）：两条都保留，置信度按来源等级调整（自述属于自我认知，成绩属于客观记录），并在画像里并列展示，让用户自己看到张力。**不做调和**——调和会制造一个双方都不认的中间结论。

**推导冲突**（两个 Agent 对同一专业得出相反的适配判断）：交给 Critic-Reviewer 判定，判定不了的降置信度并同时呈现两种观点。宁可让用户看到分歧，也不给一个虚假的统一答案。

## 6. 苏格拉底式对话的策略设计

### 6.1 提问原则

五条，按优先级 `[设计中]`：

1. **一次只问一个维度。** 「你喜欢做什么、擅长什么、看重什么」这种三连问会让考生只回答最好答的那个。
2. **问具体经历，不问抽象判断。** 「最近一次你完全忘了时间是在做什么」优于「你的兴趣是什么」。前者产出可定位的证据，后者产出不可验证的自我标签。
3. **允许「不知道」。** 明确告知可以不回答，且不追问。强迫回答会产出迎合性内容，污染画像。
4. **问反例。** 「有没有哪次你本以为会喜欢，结果很失望？」反例的信息量往往高于正例，且能防止画像单向漂移。
5. **每轮最多推进一个话题层级。** 从「做过什么」到「为什么在意」到「这意味着什么」，不跳级。

### 6.2 如何避免引导性提问污染画像

这是本节最重要的一节。引导性提问的伤害是**不可逆的**：一旦考生的回答被引导塑造，后面的所有推荐都建立在假信号上，而且系统自己无从发现。

四条机制 `[已确定]`：

**第一，Coach Agent 禁止提及具体专业名。** 一旦问「你对计算机感兴趣吗」，回答就失去了诊断价值。这个约束在工具层面强制：Coach Agent 的可用工具集里没有 `search_ekg`，它根本不知道专业列表。

**第二，问题必须双向可选。** 每个提问在生成时检查是否内含倾向。例如「你是不是更喜欢和人打交道？」是引导性的；「你更愿意花一下午独自钻研一个问题，还是和一群人讨论？」是双向的。

**第三，候选画像条目必须经用户确认（见 §5.2）。** 这是最后一道防线：即使前两道失效，用户看到「我观察到你可能喜欢 X，依据是这段话」时可以否认。

**第四，定期做引导性自检。** 对抽样会话做离线审核，统计「考生回答与提问措辞的相关性」——如果回答高度可预测，说明提问在引导。这是一项人工评估指标（见 §8.2）。

### 6.3 如何收敛话题

发散是苏格拉底式对话的天然倾向，必须主动收敛，否则永远出不了结论。

收敛信号有三个 `[设计中]`：同一话题连续两轮没有新增证据；考生开始重复已说过的内容；考生表达疲惫或明确想换话题。

收敛动作是**小结并回交控制权**：把本轮收集到的 2–3 条证据复述给考生，问「这样理解对吗」，然后给出明确的下一步选项（继续深挖／换个话题／先看看专业方向）。不替考生决定结束，但给出结束的台阶。

### 6.4 何时停止提问

四类停止条件 `[已确定]`：

第一，**证据充分。** 某个方向的稳定证据达到归纳阈值（见 §5.3），继续问的边际收益低。

第二，**考生明确要求停止。** 无条件立即停止，且不追问理由。

第三，**触发敏感边界。** 话题触及心理诊断、家庭隐私、身体状况等，立即停止并说明为什么不适合继续。文档 14 §1.4 明令禁止输出诊断类表述。

第四，**轮次上限。** 单次自我探索循环设轮次上限（具体数值待文档 11 定），到达后强制进入小结。这是防止无限对话的成本与体验保护。

## 7. 幻觉控制

四道闸门，从生成前到发布后逐层收紧。**任何一道单独都不够**，因为 LLM 幻觉的形态多样。

```text
  生成前          生成中            发布前            发布后
┌────────┐    ┌──────────┐    ┌────────────┐    ┌──────────┐
│ RAG 强制│ →  │ 结构化约束│ →  │ 确定性校验  │ →  │ 抽样回访  │
│ 引用前置│    │ 类型化输出│    │ 闸门 + Critic│    │ 与指标监控│
└────────┘    └──────────┘    └────────────┘    └──────────┘
   第 1 道        第 2 道          第 3 道           第 4 道
```

### 7.1 第一道：RAG 强制引用回填

规则很简单：**没有引用的事实断言不允许出现在最终输出里。** 实现上是生成后再做一次机械校验——把输出切成句子，识别含事实断言的句子，检查其引用编号能否回填到具体数据行。回填失败的句子删除（见 [技术架构设计](05-技术架构设计.md#42-分步说明与失败降级) 第 9 步）。

这条的代价是输出可能不连贯，收益是**系统无法说出没有出处的话**。我们接受这个代价。

### 7.2 第二道：结构化约束

Agent 之间的传递必须是类型化结果，不是自然语言（见 §1 立场三）。这阻断了幻觉的**传播**——即使某个 Agent 编了一个专业名，它在结构化校验时会被字段校验拦下，而不是被下一个 Agent 当作事实继续加工。

### 7.3 第三道：确定性校验闸门 + Critic 审核

两者分工不同。确定性校验管**可机械判定的错误**（位次算错、选科不符、计划不存在）；Critic 管**不可机械判定的错误**（断言超出证据范围、因果倒置、以偏概全）。

顺序不能颠倒：先过确定性校验，再过 Critic。因为让 Critic 去审核一个数值错误的回答是浪费，而且 Critic 本身也可能漏掉数值错误。

### 7.4 第四道：不可答时的拒答

拒答不是一个失败状态，是一个**功能**。三类拒答话术原则 `[已确定]`：

第一，**说清缺什么，不说「我不知道」。** 「要回答这个问题，我需要你所在省份 2026 年的招生计划数据，目前尚未接入」优于「抱歉我无法回答」。

第二，**给替代路径。** 「你可以先看这个专业的培养方案，选科要求需要等计划公布后确认」。

第三，**不猜测、不模糊化。** 禁止使用「一般来说」「通常情况下」来填补数据空白。这类型表述在本项目里等同于幻觉。

**我们放弃了什么：** 放弃了「尽量给答案」的体验。拒答会让对话显得不流畅，但给出一个没有依据的答案是更严重的失败。这条与文档 01 的「可拒绝」约束一致。

## 8. 编排示例

### 8.1 示例一：一次专业探索的完整编排

输入：**「我数学还行，但不想学纯数学，也不知道能干什么」**。以下所有具体专业与数值均为示例，非真实数据。

| 步 | 角色 | 动作 | 产出 | 备注 |
| --- | --- | --- | --- | --- |
| 1 | Router | 意图判定 | `major_explore`，置信度中 | 含「不知道能干什么」，需澄清但不必先澄清 |
| 2 | Personal Agent | `read_profile` | 画像：逻辑推理类证据 2 条，中等置信度；无明确职业价值取向 | 2 条证据未达归纳阈值 |
| 3 | 并行 A | Coach Agent | 澄清问题：「你说不想学纯数学，是因为不喜欢抽象证明，还是觉得就业面窄？」 | 双向可选，未提专业名 |
| 4 | 并行 B | Knowledge Retrieval Agent | `search_ekg`：结构化过滤（要求数学基础、非数学类）→ 关键词 → 向量 → 重排 → Top-8 | 示例结果：统计学、数据科学、金融数学、运筹学等方向 |
| 5 | Major Discovery Agent | 组织假设 | 3 组假设，每组含课程依据与至少 1 条反证 | 例：统计学——反证是「需较强编程习惯，画像中无相关证据」 |
| 6 | 规则闸门 | `validate_subject_requirements` | 3 组中 1 组因选科要求不满足被剔除 | 剔除项明确告知原因 |
| 7 | Critic-Reviewer | 反向审核 | 1 处「适合」表述超出证据范围，打回 | 原因码 `CLAIM_EXCEEDS_EVIDENCE` |
| 8 | Major Discovery Agent | 重写 | 将「适合」改为「与你的两条证据方向一致，但缺乏编程习惯证据」 | 第二次通过 |
| 9 | 解释生成 | 模板 + 措辞 + 引用回填 | 输出含 3 条引用，均可回填 | — |
| 10 | 写回 | L2 摘要 + 2 条画像候选 | 候选待用户确认 | 不自动生效 |

**这个示例想说明的一件事：** 第 6 步剔除发生在 LLM 组织完假设之后，而不是之前。理论上应该前置过滤，但实际实现里「考生说自己数学还行」并不构成一个可过滤的条件（没有分数），所以只能先召回再剔除。这个顺序上的不完美是当前架构的真实状态，不是示意图的简化。

### 8.2 示例二：一次志愿方案生成的编排

输入：**「我是辽宁考生，选科物化生，位次 12000 左右，想去南方，不想学医」**。数值为示例，非真实数据。

```text
考生输入
   │
   ▼
Router ──→ decision（置信度：高，字段齐全）
   │
   ├─ 缺失项检查：省份✓ 选科✓ 位次✓ 地域偏好✓ 排除项✓
   │                风险偏好✗ → 出 1 个澄清问题（同时继续执行，不阻塞）
   ▼
Decision Agent
   │
   ├──[1] query_admission_plan（辽宁 / 当年 / 物化生 / 本科批）→ 候选专业组集合
   │
   ├──[2] compute_rank 交叉校验：12000 与分数换算是否自洽
   │        └─ 不自洽 → 提示用户确认，方案标记「位次待确认」
   │
   ├──[3] validate_subject_requirements（批量）→ 剔除不符项 + 原因码
   │
   ├──[4] validate_charter_rules（批量）→ 逐条判定
   │        └─ 含「不可校验条款」清单，明确告知需人工确认
   │
   ├──[5] optimize_rms（多目标：地域 / 专业偏好 / 风险偏好）
   │        └─ 输出冲稳保分档 + 每档的约束满足状态
   │
   ▼
规则闸门二次校验（防止优化器输出越界解）
   │
   ▼
Critic-Reviewer：检查每条推荐是否都有计划数据与规则判定记录
   │
   ▼
解释生成：每档给「为什么在这个位置」的一句话说明 + 引用
   │
   ▼
输出：分档方案（含不可校验条款提示 + 缺失的风险偏好问题）
```

**这个示例想说明的一件事：** 缺失的风险偏好在第 3 步并行出澄清问题，而不是阻塞整个链路。阻塞式澄清在志愿场景体验很差——考生往往就是不知道自己的风险偏好，要求他先回答才给方案等于不给方案。我们的做法是先给一个默认风险档的方案，同时把问题抛回去，用户回答后重算。

## 9. Agent 评测方案

### 9.1 可自动化指标

| 指标 | 定义 | 目标 | 数据来源 |
| --- | --- | --- | --- |
| 引用可回填率 | 事实断言句子中引用能定位到数据行的比例 | 100% | 自动脚本逐句校验 |
| 规则闸门覆盖率 | 涉及录取判断的输出中存在规则判定记录的比例 | 100% | 决策快照审计 |
| 意图路由准确率 | 路由标签与人工标注一致的比例 | 待基线建立 `[假设]` | 标注集 |
| 打回率 | Critic 打回次数 / 总输出数 | 观察值，非目标值 | 编排日志 |
| 拒答正确率 | 应拒答而拒答 / 全部应拒答 | 待基线建立 | 构造的边界用例集 |
| 单轮成本 | 每轮 token 与工具调用折算成本 | 目标区间随阶段调整 | 账单归集 |

**注意「打回率」不设目标值。** 打回率过低可能意味着 Critic 失效，过高意味着生成质量差，两端都是问题，所以只观察趋势，不设阈值。

### 9.2 人工评估

三类 `[设计中]`：第一，**引导性审核**（§6.2 第四条），抽样会话由人工判断提问是否内含倾向；第二，**画像准确性**，请考生本人对生成的画像条目打分（认可／部分认可／不认可），这是文档 09 RQ3 的核心指标；第三，**解释可读性**，由非专业读者判断解释是否真的说清了理由。

### 9.3 评测的组织方式

以 Skill 为最小评测单位（§4.3）。同一 Skill 的不同版本（换模型、换提示词、换编排路径）在同一批固定用例上对跑，只有全部指标不劣化才允许上线。固定用例集需要覆盖：正常路径、边界（选科边界、单科成绩边界）、异常（数据缺失、规则冲突）、以及刻意构造的诱导性输入（试图让系统给出录取保证）。

## 10. 取舍与开放问题

### 10.1 明确的取舍

**取舍一：少角色、多工具，而不是多角色细分。** 我们放弃了「每个话题一个专家 Agent」的直观设计，选择七个权限边界清晰的角色。代价是单个 Agent 的职责较重、提示词较长；收益是延迟可控、审计路径短、幻觉传播面小。

**取舍二：主链路确定性优先于灵活性。** 放弃了让 Agent 自主规划路径的能力。代价是无法优雅处理特别复杂的复合请求（例如「顺便帮我看看这个学校在辽宁去年的录取情况」这类插入式请求），当前处理方式是路由到独立子任务再合并，不够优雅但可控。

**取舍三：拒答优先于可用性。** 见 §7.4。

### 10.2 开放问题

1. **Coach Agent 的「不提专业名」约束在长期对话中是否可维持。** 用户自己提到专业名时，Coach 是否可以直接接话？当前设计是可以说，但不能主动引入。这个边界的实际效果需要实证。
2. **L3 归纳的两个阈值（3 次证据、14 天）是拍脑袋的。** 见 §5.2，需要文档 09 的纵向数据校准，在此之前该设计标为 `[假设]`。
3. **Critic 只打回 1 次的规则是否足够。** 若打回率长期偏高，说明问题在生成端而非审核端，加次数无用；但也可能 1 次太少。需要观察。
4. **多 Agent 审核是否应扩展到所有输出。** 当前只在涉及录取判断时强制，纯事实查询不审。这个划分的正确性未验证（见 [技术架构设计](05-技术架构设计.md#8-当前未解决的架构难题) 第 6 条）。
5. **Admission Agent 与 University Agent 的知识库共享边界。** 两侧共用知识源，但披露边界不同。当前没有任何技术手段阻止交叉读取，只靠会话隔离与代码约定。这是一个需要在文档 08 中进一步约束的风险点。
