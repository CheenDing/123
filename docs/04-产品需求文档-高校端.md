## 1. 定位与三条边界声明

**本文定义 University Intelligence（高校端）的功能需求。它的核心不是「给高校做一个更好的官网」，而是把高校已有的专业信息从「展示材料」改造成「可被检索、可被追问、可被核对的知识」。**

三条边界声明必须先读：

1. **本项目不是任何高校、考试院或政府机构的官方系统。** 任何界面、文案、域名都不得暗示官方身份；使用高校名称须以书面授权为前提。
2. **高校端不改变、不介入任何录取流程。** 它只影响「考生如何理解专业」，不影响「高校如何录取考生」。
3. **高校端不是宣传物料生成器。** 系统只对高校提供的内容做结构化、校验与对话化，不代替高校创作宣传话术，也不生成未经核实的数据。

## 2. 从「学校中心展示」到「考生中心探索」

### 2.1 现有供给的形态与共同机制

| 形态 | 组织方式 | 主要问题 |
| --- | --- | --- |
| 官网栏目 | 按机构结构（学院—专业）组织 | 考生的问题不按机构结构提出 |
| 招生简章 PDF | 按年度成册 | 可读性差，跨年对比困难 |
| 宣讲会与直播 | 按场次、按时间 | 不可检索，不可回看细节 |
| 公众号与短视频 | 按传播节奏 | 信息碎片化，口径易漂移 |
| 电话与咨询群 | 按人力 | 高峰供给不足，回答质量随人而变 |

这些形态共享一个隐含结构：**信息按「学校怎么组织自己」排列，而考生按「我的问题」检索。** 两者不匹配的结果是：高频问题被反复回答，长尾问题无人回答，而长尾恰恰是决定考生判断的部分。

### 2.2 转变的三个具体动作

```text
  旧形态：                     新形态：
  +-----------+               +---------------------------+
  | 招生简章  |               | 结构化知识库（字段+出处）  |
  | （文档）  |  --结构化-->  |  专业 / 课程 / 规则 / 路径 |
  +-----------+               +-------------+-------------+
                                            |
  +-----------+               +-------------v-------------+
  | 电话咨询  |  --对话化-->  | 招生 Agent（有出处、可追问）|
  +-----------+               +-------------+-------------+
                                            |
  +-----------+               +-------------v-------------+
  | 统一话术  | --个性化(受限)->| 考生授权后的专业探索匹配   |
  +-----------+               +---------------------------+
```

1. **结构化**：把散落在简章、官网、院系材料里的信息，变成带字段、带出处、带年份的结构化条目，可校验、可跨年比对。
2. **对话化**：把「用户找页面」改为「用户提问题」，由招生 Agent 基于知识库回答，并允许追问。
3. **个性化但受限**：在考生主动授权的前提下，用其画像摘要辅助专业探索；授权范围与用途由考生限定。

### 2.3 取舍一：不做高校对比榜单与打分

**放弃什么：** 不做「高校排行」「专业实力评分」「A 校 vs B 校谁更好」这类功能。

**为什么：** 其一，可比的维度必须同口径，而各校培养方案、统计口径、数据年份都不同，强行打分等于制造伪精确；其二，任何排序都会被理解为评价，进而倒逼高校为榜单名次而非为培养投入内容；其三，这与「考生中心探索」的立场冲突——探索的终点是「哪个更适合我」，不是「哪个更好」。

**替代：** 提供按考生约束条件的**条件筛选**（城市、选科要求、学费区间、培养特色关键词），以及两校同一字段的**并排差异说明**，不给出优劣结论。

## 3. 高校专业知识库

### 3.1 字段需求

| 编号 | 字段组 | 关键字段 | 必填 | 来源 | 状态 |
| --- | --- | --- | --- | --- | --- |
| K1 | 专业基础 | 专业名称、专业代码、所属学院、学制、授予学位、招生专业组 | 是 | 官方专业目录 + 招生计划 | `[已确定]` |
| K2 | 培养 | 培养目标、课程结构（通识/基础/核心/实践）、能力要求、毕业要求 | 是 | 培养方案 | `[设计中]` |
| K3 | 规则 | 选科要求、单科成绩要求、体检受限、外语语种要求、转专业政策 | 是 | 招生章程 + 校内政策 | `[已确定]` |
| K4 | 发展 | 升学方向、就业去向描述、辅修与双学位可能 | 否 | 就业质量报告等公开材料 | `[规划]` |
| K5 | 特色 | 科研平台、实践基地、培养模式（如大类招生、书院制） | 否 | 院系提供 | `[规划]` |
| K6 | 招生计划 | 省份、年份、批次、科类、计划数、专业组内专业 | 是 | 省级招生计划 | `[已确定]` |

**每条字段必须携带：** 数据年份、来源标识、责任单位、最后更新时间。缺任一项视为不可发布。

### 3.2 来源分级

| 等级 | 来源 | 用途 | 约束 |
| --- | --- | --- | --- |
| S1 | 招生章程、招生计划、专业目录等正式发布文本 | 可参与规则校验与推荐 | 必须标注年份与发布单位 |
| S2 | 院系提供的培养方案、课程说明 | 可用于内容展示与匹配解释 | 需招生办确认口径 |
| S3 | 在校生提供的学习体验描述 | 仅用于「典型学习体验」区块 | 显著标注为非官方，不参与规则判定 |

### 3.3 缺失与冲突处理

- **缺失：** 显示「暂无公开数据」，禁止用模型生成内容补齐。
- **冲突：** 以最新正式发布文本为准，保留旧版本与生效时间，界面上标注「口径已更新」。
- **过期：** 超过设定时效（按字段类型区分，由[知识与数据建模](07-知识与数据建模.md#33-置信度分档定义)定义）自动标记「待更新」，并在考生端显示提示。

### 3.4 内容审核工作流

```text
 院系提交 ──> 招生办审核 ──> 自动校验 ──> 发布 ──> 版本留痕
    |             |              |           |          |
    |             |              +-- 字段完整性      |  可回溯
    |             |              +-- 与规则库一致性  |  可回滚
    |             +-- 口径确认                     |
    +-- 附带来源与年份                            +-- 考生端可见
```

**要求：** 任何字段的发布都必须经过「字段完整性」与「与规则库一致性」两项自动校验；校验不通过不得发布，但可保存草稿。

## 4. 招生 Agent 的能力边界

### 4.1 能力分层

| 层级 | 能做什么 | 硬性要求 | 状态 |
| --- | --- | --- | --- |
| L1 可答 | 回答招生计划、选科要求、培养方案要点、转专业政策 | 每条回答必须给出处（文档名 + 年份 + 段落定位） | `[设计中]` |
| L2 可推 | 跨条目推理：课程 → 能力 → 适合什么样的学生 | 必须显式标注「以下为基于公开材料的推断」 | `[设计中]` |
| L3 可引导 | 无法回答时引导至官方渠道或转人工 | 必须给出具体渠道，不得以「建议咨询学校」敷衍 | `[设计中]` |
| L4 必拒 | 录取可能性判断、分数线预测、他校比较评价、未公开信息 | 拒答必须说明原因，并给出可替代的可行问题 | `[已确定]` |

### 4.2 FAQ 之上还能做什么

FAQ 是「一问一答」的检索；招生 Agent 的增量价值在三件事：

1. **条件化回答**：同一个问题在不同省份、不同选科、不同批次下答案不同，Agent 需先确认约束再回答，而不是给一段通用话术。
2. **跨条目串联**：把「这门课学什么」「这个方向要什么能力」「什么背景的学生学起来更顺」串成一条可读的解释。
3. **不确定性的诚实表达**：明确说出「这份材料是 20XX 年的」「该信息未在公开材料中找到」，而不是编一个像样的答案。

### 4.3 绝对不能做

| 禁止项 | 说明 |
| --- | --- |
| 录取承诺 | 任何「你报我们一定能录」「稳上」类表述 |
| 分数预测 | 不做「明年大概多少分」类判断 |
| 贬低他校 | 不做校际比较评价，不评价其他高校 |
| 代表学校表态 | 涉及政策解释、承诺性内容一律转人工 |
| 心理判断 | 不评价考生的能力高低、性格适合与否 |

### 4.4 幻觉控制要求

- 检索无结果时不生成答案，直接进入 L3 引导。
- 规则类问题（选科、体检、单科要求）必须走确定性规则引擎，不由 LLM 直接作答。
- 回答中的每个事实性断言都必须能回填到知识库条目；回填失败即视为不可发布。
- 多轮对话中，若用户问题超出知识库范围，宁可短答，不可延伸。

### 4.5 验收口径

见 §9 的 `AC-U-01`–`AC-U-03`。

## 5. 个性化专业匹配：授权与隐私边界

### 5.1 授权模型

**默认状态：不授权。** 考生画像对高校侧完全不可见，除非考生主动发起并逐项选择。

| 要素 | 要求 |
| --- | --- |
| 发起方 | 必须是考生本人，高校侧不得主动请求 |
| 粒度 | 逐条选择可披露的画像条目，支持全不选 |
| 用途 | 仅限「专业探索与咨询」，用途写入授权记录 |
| 期限 | 默认短期有效，到期自动失效 |
| 撤回 | 一键撤回，立即生效 |
| 技术载体 | 以**授权令牌**（授权 ID + 场景 + 期限 + 字段集）随请求下发，过期即失效且不自动续期，见[数据治理隐私与合规](08-数据治理隐私与合规.md) §6.2 与[技术架构设计](05-技术架构设计.md) §7 |

### 5.2 可见与不可见

| 高校侧可见 | 高校侧不可见 |
| --- | --- |
| 考生主动选中的画像条目标签与摘要（**不含原始证据片段**） | 考生身份信息（姓名、证件号、联系方式） |
| 考生主动填写的咨询问题 | 未被选中的画像条目 |
| 对话中的追问内容 | 对话原文的完整留存（仅保留脱敏统计） |
| 聚合后的咨询主题分布 | 任何可用于识别个体的组合信息 |

> 字段白名单与状态白名单以[数据治理隐私与合规](08-数据治理隐私与合规.md) §6.1 为准；本文只约定「考生可逐项选择」这一交互前提。

### 5.3 四条红线

1. **不得用于录取决策**：授权数据不得进入任何录取、分班、奖学金评定流程。
2. **不得二次分发**：不得导出、转发、用于第三方系统。
3. **不得用于排序与筛选**：不得据此对考生排序、分级或决定谁获得回复。
4. **不得回写考生画像**：高校侧的任何操作不得修改考生侧画像条目。

### 5.4 撤回后的级联行为

```text
 考生撤回授权
      |
      +--> 高校侧授权视图立即失效（会话中断，不可再查询）
      +--> 会话态数据（授权视图、原始画像片段）会话结束即不落库、不可回溯
      +--> 已产生的咨询记录去标识化保留（仅保留主题与问题类型，
             仅用于聚合统计、不含个体可识别字段，最小分组阈值见文档 08 §7.1）
      +--> 考生侧记录一次撤回事件，可查看授权历史
```

### 5.5 待验证假设

`[假设]` 高校是否愿意接受「只能看到授权摘要」的受限视图。验证方式：在试点沟通中直接提出该方案，记录异议点与替代诉求；若高校普遍要求更多数据，则本项目应坚持边界并接受接入意愿下降的代价，而非放宽边界。这一点需要 Lead 在收口阶段确认立场。

## 6. 招生部门管理后台

### 6.1 角色与权限

| 角色 | 权限 | 限制 |
| --- | --- | --- |
| 内容编辑（院系） | 提交与修改本科专业内容 | 不能直接发布 |
| 审核员（招生办） | 审核、发布、回滚 | 不能修改授权数据 |
| 管理员 | 账号与权限管理、规则集配置 | 操作全量留痕 |
| 观察者 | 查看统计与内容缺口 | 只读 |

### 6.2 三项核心功能

| 编号 | 功能 | 说明 | 状态 |
| --- | --- | --- | --- |
| U1 | 内容维护 | 结构化字段录入优先于富文本；富文本仅用于补充说明 | `[设计中]` |
| U2 | 知识库校验 | 发布前的完整性与一致性检查，输出问题清单而非笼统报错 | `[设计中]` |
| U3 | 咨询分析 | 脱敏聚合的高频问题、未答问题、内容缺口，反向指导内容生产 | `[规划]` |

### 6.3 咨询分析看板（示意）

```text
+--------------------------------------------------------------+
| 咨询分析 · 近 30 天（示例布局，数值为示意）                   |
+--------------------------------------------------------------+
| 高频问题 TOP：转专业政策 / 大类分流规则 / 保研比例口径        |
| 未答问题（需补内容）：XX 方向课程难度 / 实验班选拔时间        |
| 内容缺口建议：补充「大类招生分流时间表」，当前无结构化字段    |
| 拒答原因分布：超出知识库范围 / 涉及录取判断 / 涉及他校比较    |
+--------------------------------------------------------------+
| [导出脱敏报表]   [生成内容补充任务]                           |
+--------------------------------------------------------------+
```

**要点：** 「未答问题」清单是后台对高校最有价值的部分——它把「考生问不出来、也问不到」的盲区变成了可执行的内容任务。

## 7. 东北大学试点场景的范围界定

### 7.1 前提声明

东北大学是本项目的**试点场景**，属于合作意向与建设设想，**不是校方官方服务**，也未获得任何官方身份授权用于对外宣传。本节不写任何真实专业设置、师资、分数、计划数；相关数据须由校方提供并书面授权后方可使用。

### 7.2 试点验证什么

| 编号 | 待验证问题 | 观察方式 | 状态 |
| --- | --- | --- | --- |
| P1 | 把院系材料结构化为知识库字段，实际人力成本有多高 | 记录单个专业的录入与审核工时 | `[假设]` |
| P2 | 招生 Agent 能承接多大比例的高频咨询 | 对比引入前后的咨询量与转人工比例 | `[假设]` |
| P3 | 考生是否愿意用对话而非搜索来了解专业 | 对话轮次与追问率 | `[假设]` |
| P4 | 授权摘要是否足以支撑一次有意义的专业咨询 | 咨询后考生自评与高校侧反馈 | `[假设]` |

### 7.3 范围

| 在范围内 | 不在范围内 |
| --- | --- |
| 少数院系、少数专业的知识库建设 | 全校全专业一次性接入 |
| 招生 Agent 的问答与引导能力 | 录取流程系统的任何对接 |
| 考生授权后的专业探索匹配 | 招生宣传物料制作与投放 |
| 咨询分析与内容缺口反馈 | 招生策略建议与生源质量预测 |

### 7.4 试点判据

**成功信号（定性）：** 院系能在无外部专家长期驻场的情况下独立完成内容提交；招生办能基于「未答问题」清单发起内容补充；考生在对话中产生追问而不是问完即走。

**失败信号：** 内容维护成本高到院系不愿持续投入；Agent 拒答比例高到被当作「没用」；高校要求放宽授权边界作为接入前提。任一失败信号出现，应先修正方案而不是扩大范围。

## 8. 多高校接入的扩展性

### 8.1 三层接入

| 层级 | 内容 | 接入成本主要在哪 |
| --- | --- | --- |
| 数据接入 | 招生计划、选科要求、录取数据等结构化字段 | 数据口径对齐与授权 |
| 内容接入 | 专业一页纸内容（培养、课程、特色） | 院系撰写与审核 |
| Agent 接入 | 对话能力与话术风格 | 配置与测试 |

### 8.2 配置化与定制化的边界

- **可配置：** 字段映射、规则集、话术风格、展示顺序偏好、时效阈值。
- **不可配置（必须人工）：** 培养方案的语义解析、专业特色的表述、任何涉及口径判断的内容。

**取舍：** 我们放弃「一套模板自动适配所有高校」的想法。招生规则与培养体系的差异不是配置项能吸收的，强行模板化会产出「看起来整齐、实际错漏」的内容，而错误信息的代价远高于接入成本。

### 8.3 中立性要求

- 多校同时呈现时，顺序不得与商业合作关系挂钩；必须写明排序依据（如按考生约束匹配度、按字母序）。
- 不做「推荐报考」类引导，只做「条件匹配」说明。
- 任何高校不得付费获得排序优势——若未来引入商业化，须有独立的中立性条款，且不得影响考生端结论。
