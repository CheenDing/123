## 1. 建模立场

**问题：** 为什么要有两个知识图谱，一个不够吗？

**简明答案：** 因为教育知识图谱（Education Knowledge Graph，EKG）与个人知识图谱（Personal Knowledge Graph，PKG）回答的是两类根本不同的问题，混在一起会让「事实」和「判断」失去边界。

EKG 回答「世界上有什么」：有哪些高校、哪些专业、这个专业学什么课、往年录取到什么位次。它的特点是**客观、可溯源、多人共享、版本可对比**。

PKG 回答「这个人是谁」：他关心什么主题、有哪些能力线索、看重什么、哪些结论还只是猜测。它的特点是**主观、随证据变化、单人私有、必须可撤回**。

把两者放在一张图里的后果很具体：一条录取记录和一条「考生喜欢生物」的断言会成为同构的节点，而前者不该被删除、后者必须可以被用户删除。文档 08 的合规要求在这张混图上无法实现。所以两图分离，用**对齐层**（Alignment Layer）连接，见 §4 `[已确定]`。

三条建模原则：

第一，**每个事实都要能溯源到一个数据来源等级。** 没有来源等级的数据不可入库，不是「入库后标记」，而是入库时必填。

第二，**每个判断都要能溯源到证据集合。** 画像条目没有证据就只是猜测，必须显式标注为待验证假设。

第三，**schema 要能承载「不可用」。** 招生章程里存在无法机械判定的条款，模型必须能表达「这条存在但无法校验」，而不是丢弃或强行判定。

## 2. 教育知识图谱 EKG

### 2.1 实体清单

| 实体 | 标识 | 关键属性 | 主要来源 |
| --- | --- | --- | --- |
| 高校 University | `university_id` | 名称、曾用名、所在地、办学层次、主管部门 | 官方公开信息 |
| 学院 College | `college_id` | 名称、所属高校 | 高校官网 |
| 专业 Major | `major_id` | 名称、专业代码、所属学科门类、修业年限、授予学位 | 教育部专业目录 |
| 学科 Discipline | `discipline_id` | 门类／一级学科代码、名称 | 学科目录 |
| 课程 Course | `course_id` | 名称、课程性质、学分、学时、先修要求 | 培养方案 |
| 培养方案 Curriculum | `curriculum_id` | 适用年份、总学分、培养目标、毕业要求 | 高校培养方案 |
| 师资 Faculty | `faculty_id` | 所属单位、职称类别、研究方向 | 高校官网 |
| 科研平台 Platform | `platform_id` | 名称、级别、所属单位 | 高校官网 |
| 招生计划 Plan | `plan_id` | 省份、年份、科类／选科、批次、专业组、计划数 | 省级考试院／高校 |
| 录取记录 Record | `record_id` | 省份、年份、科类、批次、最低分、最低位次 | 省级考试院公开数据 |
| 职业 Occupation | `occupation_id` | 名称、职业分类、典型能力要求 | 职业分类目录 |
| 数据来源 Source | `source_id` | 来源类型、获取时间、适用口径、可信度等级 | 采集元信息 |

**关于「专业」与「学科」的严格区分。** 这是术语表（文档 14 §2）的强制要求，也是建模上必须落地的约束：学科是知识分类，专业是培养单位。一个专业可以依托一个或多个学科，一个学科可以支撑多个专业。这个关系在检索时很关键——考生说「我对生物感兴趣」，命中的是**学科**，而推荐给考生的是**专业**，中间必须有一次显式映射 `[已确定]`。

### 2.2 关系清单

| 关系 | 起点 → 终点 | 基数 | 说明 |
| --- | --- | --- | --- |
| 设有 | 高校 → 学院 | 1:N | — |
| 开设 | 学院 → 专业 | 1:N | 同一专业名在不同高校是不同实体 |
| 依托 | 专业 → 学科 | N:M | 一个专业可依托多个学科 |
| 包含课程 | 培养方案 → 课程 | N:M | 带学分、学期、必修／选修 |
| 属于 | 专业 → 培养方案 | 1:N | 按年份版本化 |
| 任教 | 师资 → 学院 | N:1 | — |
| 承担 | 师资 → 课程 | N:M | 可选，依数据可得性 |
| 隶属 | 科研平台 → 学院 | N:1 | — |
| 招生 | 招生计划 → 专业组 | N:1 | 计划是年度、分省的 |
| 录取 | 录取记录 → 专业组 | N:1 | 与计划同口径 |
| 通向 | 专业 → 职业 | N:M | **弱关系，需标注依据强度** |
| 源自 | 任意实体 → 数据来源 | N:1 | 溯源必备 |

**「通向」关系需要特别标注。** 专业到职业的映射在现实中高度不确定，且容易被误读为「读这个专业就能做这个职业」。建模上把它设为弱关系，带 `basis` 字段（取值为「官方职业分类对照」「培养目标原文」「人工推断」），且在前端展示时必须带「这不是就业保证」的提示。这条与文档 14 §1.3 的禁止效果承诺一致。

### 2.4 为什么不做「一个巨型本体」

一个诱人的方案是把所有教育概念建成一个统一本体，然后所有查询都走本体推理。我们明确放弃这条路 `[已确定]`，理由有三：其一，招生规则以省为单位高度异构，统一本体无法承载省份差异，最终会在属性里塞满 `province_specific_*` 字段；其二，本体推理的可解释性对非技术读者极差，招生办无法复核；其三，维护成本随覆盖面超线性增长。**当前选择：核心实体用严格 schema，省份差异用扩展字段承载，不做自动推理，对齐逻辑显式写在代码里。**

## 3. 个人知识图谱 PKG

### 3.1 实体与节点类型

| 节点类型 | 标识 | 关键属性 | 来源 |
| --- | --- | --- | --- |
| 兴趣主题 Interest Topic | `topic_id` | 主题名、关联的学科知识点、首次出现时间、当前状态 | 从证据归纳 |
| 证据 Evidence | `evidence_id` | 原文片段、来源类型、定位、时间戳、所属会话 | 对话／任务记录／授权导入 |
| 能力线索 Capability Signal | `signal_id` | 能力维度、强度档、证据集合 | 从证据归纳 |
| 价值观 Value | `value_id` | 价值维度、倾向方向、证据集合 | 从证据归纳 |
| 假设 Hypothesis | `hypothesis_id` | 假设内容、验证状态、验证方式 | Agent 提出，用户可否认 |
| 画像条目 Profile Entry | `entry_id` | 条目类型、内容、置信度、证据集合、状态 | 上述归纳产出 |

### 3.2 验证状态机

假设节点是 PKG 与普通标签系统的本质区别：它允许「不确定」显式存在 `[设计中]`。

```text
   [提出]
      │
      ▼
  ┌────────┐  新增支持证据   ┌──────────┐  证据充分   ┌──────────┐
  │ 待验证  │ ─────────────→ │ 验证中    │ ─────────→ │ 已确认    │
  │Pending │                │Verifying │            │Confirmed │
  └───┬────┘                └────┬─────┘            └────┬─────┘
      │  用户否认                │  出现反证               │ 长期未再出现
      ▼                          ▼                        ▼
  ┌────────┐                ┌──────────┐            ┌──────────┐
  │ 已否决  │                │ 存在矛盾  │            │ 衰减归档  │
  │Rejected│                │Contradict│            │ Archived │
  └────────┘                └────┬─────┘            └──────────┘
                                 │ 用户裁定
                                 ▼
                            已确认 / 已否决
```

「存在矛盾」是一个**正常状态**，不是错误。系统不应该急着消解它（见 [多智能体与Agent设计](06-多智能体与Agent设计.md#54-冲突消解)）。

### 3.3 置信度分档定义

文档 14 §2 要求置信度分档在本文定义。定义如下 `[设计中]`：

| 档位 | 判定条件 | 可被谁使用 | 展示要求 |
| --- | --- | --- | --- |
| 高 High | ≥3 条独立证据，跨 ≥14 天，无有效反证，用户已确认 | 可作为专业探索主依据；可作为志愿方案的辅助约束 | 可简化依据展示 |
| 中 Medium | 2 条证据，或 1 条强证据（如长期行为记录），用户已确认 | 可用于探索方向提示；**不得**单独作为志愿方案约束 | 必须展示证据摘要 |
| 低 Low | 1 条证据，或证据来源为单次自述，未确认 | 仅可用于提问线索，**不得**出现在推荐理由中 | 必须展示证据原文 + 「仅为初步观察」 |

三条硬规则：第一，用户否认过的条目直接进「已否决」，不复用；第二，未确认的候选条目不参与任何推荐计算，只作展示；第三，**低置信度条目禁止作为任何结论的唯一依据**。这三条对应文档 06 §5.2 的写入策略，两侧必须一致 `[已确定]`。

## 4. 两图对齐机制

### 4.1 对齐要解决的问题

考生的语言是「我喜欢看星星、喜欢解谜」，EKG 的语言是「天文学（学科）」和「数据科学与大数据技术（专业）」。对齐层要做的是把前者映射到后者，且映射必须**可解释、可质疑、可替换**。

### 4.2 三层对齐路径

```text
  PKG 侧                             对齐层                         EKG 侧
  ┌──────────────┐                                          ┌──────────────┐
  │ 兴趣主题      │ ──①主题→知识点──→  ┌──────────────┐      │ 学科知识点    │
  │ Topic        │                    │ 主题-知识点    │ ───→ │ Knowledge Pt │
  └──────────────┘                    │ 映射表         │      └──────┬───────┘
                                      │              │             │ ②知识点
  ┌──────────────┐                    │ 每行含：       │             ▼  →课程
  │ 证据 Evidence │ ─────────────────→ │ 来源（人工/LLM）│      ┌──────────────┐
  └──────────────┘   支撑              │ 置信度         │      │ 课程 Course   │
                                      │ 审核状态       │      └──────┬───────┘
  ┌──────────────┐                    └──────────────┘             │ ③课程
  │ 能力线索      │ ──④能力→培养要求─────────────────────→          ▼ →专业
  │ Capability   │                                          ┌──────────────┐
  └──────────────┘                                          │ 专业 Major    │
                                                            └──────────────┘
```

四段路径的粒度不同，可靠性也不同：

**① 主题 → 学科知识点。** 最不可靠的一段。由 LLM 产出候选映射，人工抽检，置信度按映射表标注。「喜欢解谜」映射到「逻辑推理」「算法思维」这类知识点，本身是推断而非事实。

**② 知识点 → 课程。** 较可靠。课程大纲的知识点覆盖有一定客观性，但仍需人工确认课程实际讲授内容。

**③ 课程 → 专业。** 最可靠。培养方案的课程结构是官方文件，可直接依 `包含课程` 关系推导。

**④ 能力线索 → 培养要求。** 方向与 ① 相反，是从个人到要求。这一段的判断最容易过度自信，因此在实现上**必须落回具体课程或培养方案条目**，不允许停留在「能力匹配」这样抽象的说法。这也正是文档 05 §2.2 灰色地带处理规则的具体落点。

### 4.3 映射表的结构与治理

映射是数据，不是代码。这一点很关键：映射会随认知变化，硬编码在代码里会让每次修正都变成发版。

| 字段 | 含义 | 示例（示例，非真实数据） |
| --- | --- | --- |
| `mapping_id` | 映射标识 | `map_0001` |
| `from_type` / `from_id` | 起点 | `topic` / `topic_观星` |
| `to_type` / `to_id` | 终点 | `knowledge_point` / `kp_天体物理基础` |
| `basis` | 依据 | `人工标注` / `LLM 候选` / `培养方案原文` |
| `confidence` | 置信度档 | `低` |
| `review_status` | 审核状态 | `待审` / `已审` / `已否决` |
| `version` | 映射版本 | `v3` |

**取舍：** 我们放弃了「自动学习映射」的方案，选择人工审核 + LLM 候选的半自动路径。代价是映射覆盖速度慢，收益是每一段对齐都能被追问「凭什么这么映射」。在 Phase 1 的规模下这个代价可以接受 `[假设]`；如果映射表规模增长到无法人工审核，这个决定需要重审。

## 5. 核心数据模型

以下为设计示例，字段可调整。**所有示例值均标注「示例，非真实数据」。**

### 5.1 培养方案 `ekg_curriculum`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `curriculum_id` | string | 主键 |
| `major_id` | string | 外键 → 专业 |
| `university_id` | string | 冗余，便于按校查询 |
| `apply_year` | int | 适用年份，同一专业多年份多版本 |
| `total_credits` | number | 总学分 |
| `degree_awarded` | string | 授予学位 |
| `training_objectives` | text | 培养目标原文（不得改写） |
| `graduation_requirements` | jsonb | 毕业要求条目数组 |
| `source_id` | string | 外键 → 数据来源 |

### 5.2 课程 `ekg_course`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `course_id` | string | 主键（同名课程按高校去重） |
| `university_id` | string | 开课单位 |
| `course_name` | string | 课程名 |
| `course_type` | enum | 必修 / 选修 / 实践 |
| `credits` / `hours` | number | 学分 / 学时 |
| `knowledge_points` | jsonb | 覆盖的知识点数组，对齐用 |
| `prerequisites` | jsonb | 先修课程标识数组 |

**「先修要求」字段的设计价值：** 考生常问「我数学不好能不能学这个」。先修要求能给出结构性回答（「本专业前两学期有高等数学与线性代数」），比模糊的「需要较强数学基础」有用得多，且可溯源。

### 5.3 录取记录 `ekg_admission_record`

口径字段是这张表的生命线。**缺任一必填口径字段的记录视为不可用**（对应文档 14 §5.3）。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `record_id` | string | 主键 |
| `university_id` / `major_group_id` | string | 录取对象 |
| `province` | string | **必填** 省份 |
| `year` | int | **必填** 年份 |
| `subject_track` | string | **必填** 科类或选科组合 |
| `batch` | string | **必填** 批次 |
| `min_score` / `min_rank` | number | 最低分 / 最低位次 |
| `plan_count` / `actual_count` | int | 计划数 / 实际录取数 |
| `source_id` | string | **必填** 来源 |

**为什么 `min_rank` 比 `min_score` 更重要。** 分数跨年不可比（试题难度、考生人数变化），位次相对稳定。系统所有涉及录取可行性的判断以位次为主依据，分数仅作展示与交叉校验 `[已确定]`。志愿方案的冲（Reach）、稳（Match）、保（Safety）分档，全部以位次为计算基准。这也决定了 `compute_rank` 工具在架构中的地位（见 [多智能体与Agent设计](06-多智能体与Agent设计.md#42-工具清单)）。

### 5.4 招生计划 `ekg_admission_plan`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `plan_id` | string | 主键 |
| `university_id` | string | 高校 |
| `major_group_id` | string | 专业组 |
| `major_ids` | jsonb | 组内专业 |
| `province` / `year` / `batch` | — | **必填** 口径 |
| `subject_requirements` | jsonb | 选科要求（含「或」「必选」等逻辑） |
| `plan_count` | int | 计划数 |
| `charter_ref` | string | 关联招生章程条款标识 |

`subject_requirements` 的结构必须能表达选科的布尔逻辑，例如「物理必选，化学与生物二选一」。用纯文本存储会让规则引擎无法判定，用扁平数组会丢失逻辑关系。设计上用表达式树 `[设计中]`：

```json
{
  "expr": "AND",
  "children": [
    {"expr": "REQUIRED", "subject": "physics"},
    {"expr": "OR", "children": [
      {"expr": "REQUIRED", "subject": "chemistry"},
      {"expr": "REQUIRED", "subject": "biology"}
    ]}
  ]
}
```

### 5.5 画像条目 `profile_entry`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `entry_id` | string | 主键 |
| `candidate_id` | string | 考生标识 |
| `entry_type` | enum | 兴趣主题 / 能力线索 / 价值观 / 假设 |
| `content` | jsonb | 结构化内容（非自由文本） |
| `confidence_tier` | enum | `high` / `medium` / `low`，定义见 §3.3 |
| `evidence_ids` | jsonb | **必填** 依赖的证据集合 |
| `status` | enum | 待验证 / 验证中 / 已确认 / 已否决 / 存在矛盾 / 归档 |
| `supersedes` | string | 被本条目取代的旧条目（不覆盖，只标记） |
| `created_at` / `updated_at` | timestamp | — |

```json
{
  "entry_id": "pe_示例_0001",
  "entry_type": "interest_topic",
  "content": {
    "topic": "生命科学",
    "knowledge_point_ids": ["kp_示例_细胞", "kp_示例_遗传"],
    "note": "（示例，非真实数据）多次提及对细胞与遗传机制的关注"
  },
  "confidence_tier": "medium",
  "evidence_ids": ["ev_示例_001", "ev_示例_014"],
  "status": "已确认"
}
```

`supersedes` 而非覆盖式更新，是为了让「用户的看法曾经变过」这件事可被追溯。这与文档 06 §5.4 的冲突消解策略一致。

## 6. 数据来源分级

来源等级不是标签，它直接决定数据能否使用、如何使用 `[已确定]`。

| 等级 | 定义 | 典型来源 | 使用限制 |
| --- | --- | --- | --- |
| S1 官方 | 省级考试院、教育主管部门、高校官方发布的正式文件 | 招生计划汇编、一分一段表、专业目录 | 可作为录取判断的唯一依据 |
| S2 半官方 | 高校官网、招生宣传材料、培养方案页面 | 专业介绍、课程列表 | 可作事实依据；涉及录取判断需 S1 交叉验证 |
| S3 用户生成 | 考生自述、对话内容、用户授权导入的第三方记录 | 对话、日记、导入记录 | 仅可作为画像证据；不得作为专业事实 |
| S4 人工标注 | 由项目团队整理、标注的映射与说明 | 主题-知识点映射、职业对照 | 必须标注标注人与审核状态 |
| S5 待核 | 来源不明或未经核验的采集数据 | 网络二手转载 | **不得进入对外输出**，仅可内部参考 |

**硬规则：** 任何进入 LLM 上下文的片段必须携带 `source_level`；LLM 输出不得引用 S5 数据；涉及录取可行性的断言必须只基于 S1。这条在架构上由 Knowledge Retrieval Agent 保证（见文档 06 §2.2）。

## 7. 混合检索设计

### 7.1 五段链路

```text
  查询
   │
   ▼
┌──────────────────┐   产出：候选集 A（已满足硬约束）
│ ① 结构化过滤      │   输入：省份/年份/科类/选科/批次/学科门类
│ Structured Filter│   失败 → 降级为「仅按省份年份过滤」并标注
└────────┬─────────┘
         ▼
┌──────────────────┐   产出：候选集 B（关键词命中，带 BM25 分）
│ ② 关键词检索      │   失败 → 跳过该段，向量段权重上调
│ Keyword (BM25)   │
└────────┬─────────┘
         ▼
┌──────────────────┐   产出：候选集 C（语义近邻）
│ ③ 向量检索        │   失败 → 仅用 B，标注「语义检索降级」
│ Vector           │
└────────┬─────────┘
         ▼
┌──────────────────┐   产出：合并重排后的 Top-K
│ ④ 融合与重排      │   策略：RRF 或加权；重排模型不可用 → 用规则打分
│ Fusion & Rerank  │
└────────┬─────────┘
         ▼
┌──────────────────┐   产出：带引用的片段
│ ⑤ 引用回填        │   每片段挂 source_id + 数据版本 + 定位
│ Citation Backfill│   失败 → 该片段不得进入输出
└──────────────────┘
```

### 7.2 各环节的降级策略

**降级不是「出错就算了」，而是「换一种方式继续，并把降级状态传给上层」。** 上层据此调整置信度与提示文案。

| 环节 | 失败情形 | 降级动作 | 对用户可见的影响 |
| --- | --- | --- | --- |
| ① 结构化过滤 | 该省份该年份口径数据缺失 | 放宽到「同省份近三年」，标注年份差异 | 结果标注「基于往年口径」 |
| ② 关键词 | 索引不可用 | 跳过，向量权重上调 | 精确专业名可能漏召回 |
| ③ 向量 | 嵌入服务不可用 | 仅关键词 + 结构化，标注降级 | 自然语言描述易漏召回 |
| ④ 重排 | 重排模型超时 | 用规则打分（来源等级 + 关键词覆盖 + 新鲜度） | 排序质量下降，标注「未重排」 |
| ⑤ 引用回填 | 定位信息缺失 | 该片段丢弃，不进入输出 | 信息量下降，但无可信度损失 |

**关键设计：第 ⑤ 段的降级是「丢弃」而不是「标注」。** 其他四段失败都能靠标注来补偿，唯独引用回填失败不能——一个没有出处的片段进入输出，等于把幻觉伪装成事实。这条与文档 06 §7.1 一致。

### 7.3 为什么结构化过滤必须前置

考虑一个具体例子：考生选科是「物理 + 生物 + 地理」，系统推荐了一个要求「物理 + 化学」的专业。如果过滤在前，这个专业根本不会进入候选集；如果过滤在后，它会先被召回、被重排排到前面、被 LLM 写进解释，最后才在校验阶段被剔除——此时用户可能已经读到了那段解释。

**前置的收益是消除「说了再删」的体验伤害，代价是召回空间被硬约束压缩，可能漏掉一些「其实可报」的专业**（例如某些专业组内不同专业选科要求不同）。我们接受这个代价，因为它是**向保守方向**的误差：漏掉一个可报专业，用户少一个选项；推荐一个不可报专业，用户可能因此退档。两者后果不对称 `[已确定]`。

## 8. 数据质量校验规则

校验分三层：入库时、检索时、输出前。每层职责不同，不能合并。

| 编号 | 规则 | 层级 | 失败处理 |
| --- | --- | --- | --- |
| Q1 | 录取记录必填口径字段（省份/年份/科类/批次/来源）完整 | 入库 | 拒绝入库，记入待修队列 |
| Q2 | 位次单调性：同省份同年份，分数降序与位次序一致 | 入库 | 标记矛盾，人工复核，暂不对外 |
| Q3 | 招生计划数 ≥ 0 且 ≤ 该专业组总计划 | 入库 | 拒绝入库 |
| Q4 | 选科要求表达式可解析且非空 | 入库 | 拒绝入库 |
| Q5 | 培养方案年份与专业存续期一致 | 入库 | 标记，人工复核 |
| Q6 | 同一实体多来源冲突（如两处总学分不同） | 入库 | 保留高等级来源，低等级登记冲突 |
| Q7 | 引用回填目标在库中存在且版本一致 | 检索 | 丢弃该片段 |
| Q8 | 检索结果来源等级 ≥ 当前场景要求 | 检索 | 过滤 |
| Q9 | 输出中每条事实断言有 ≥1 条引用 | 输出前 | 删句 |
| Q10 | 输出中「通向职业」类表述带弱关系声明 | 输出前 | 补声明或删除该句 |
| Q11 | 画像条目证据集合非空 | 写入 | 拒绝写入 |
| Q12 | 画像条目置信度与证据数量匹配（见 §3.3） | 写入 | 降档 |

**Q2 值得单独说。** 位次单调性校验能捕获相当一部分数据录入错误——如果某条记录的分数比另一条高但位次更低，至少有一条是错的。这个校验不需要外部真值，纯靠内部一致性，成本极低而收益明显 `[已确定]`。

## 9. 图谱版本管理与演进

### 9.1 为什么要版本化

三类变更必须可回溯 `[设计中]`：数据变更（今年的招生计划与去年不同）、schema 变更（新增字段或改变语义）、映射变更（主题到知识点的对应关系调整）。

**没有版本的后果很具体：** 用户三个月前得到的推荐，现在回看发现理由对不上，而系统无法解释这是因为数据更新了还是因为当时算错了。这直接摧毁可追溯性。

### 9.2 版本模型

```text
  数据批次 Batch ──→ 数据集版本 Dataset Version ──→ 快照 Snapshot
       │                      │                          │
       │ 采集时间              │ 语义版本                  │ 供回放使用
       │ 来源清单              │ 变更说明                  │ 只读
       ▼                      ▼                          ▼
  src_2026_ln_01         ekg_v2026.11              snap_20261115
```

三条规则：第一，**EKG 只在批次边界更新**，不做单条实时写入，保证任意时刻的查询看到的是一个自洽版本；第二，**schema 变更必须升主版本**，且保留旧版本读取能力至少一个周期；第三，**决策快照引用具体数据集版本**，回放时用当时的版本而非当前版本（对应文档 05 §7.2 的决策快照）。

**取舍：** 放弃实时更新意味着数据新鲜度有延迟（招生计划公布后需等一个批次才能生效）。代价是「用户查询时可能拿到上一批次数据」。收益是任意一次查询都可复现、可回放。在招生数据这种**年度更新、变更集中**的场景里，这个取舍是合适的 `[假设]`；如果未来接入需要高频更新的数据源，需重新评估。

### 9.3 PKG 的版本策略

PKG 不按批次版本化，但每条画像条目保留完整变更历史（`supersedes` 链 + 时间戳）。理由：EKG 是共享事实，需要一致性；PKG 是个人判断，需要可追溯的演变，不需要全局一致。

## 10. 取舍与开放问题

### 10.1 明确的取舍

**取舍一：两图分离而非统一图谱。** 见 §1。放弃了跨图一次性查询的便利，获得的是「事实不可删、判断可撤回」的合规能力。

**取舍二：核心实体严格 schema，省份差异用扩展字段。** 见 §2.4。放弃了统一本体与自动推理，获得的是可维护性与可解释性。代价是省份扩展字段会成为技术债，需要在文档 08 的数据治理里持续清理。

**取舍三：映射人工审核而非自动学习。** 见 §4.3。放弃了覆盖速度，获得每一段对齐的可质疑性。

**取舍四：结构化过滤前置，接受漏召回。** 见 §7.3。这是一个**向保守方向**的不对称取舍。

### 10.2 开放问题

1. **主题到知识点的映射缺乏评估基准。** 怎么判断「喜欢解谜 → 逻辑推理」这个映射是对的还是错的？没有真值，只能靠专家一致性与用户认可度，而两者都可能系统性偏离（同 [技术架构设计](05-技术架构设计.md#8-当前未解决的架构难题) 第 1 条）。
2. **置信度分档的阈值（3 条证据、14 天）是拍脑袋的。** 由[文档 09](09-研究与评估方案.md) RQ1/RQ2 的纵向观察与[文档 11](11-MVP实验与验收标准.md) 的 MVP 数据共同校准；档位阈值不要求在 MVP 前定稿，在此之前标为 `[假设]`。
3. **「通向职业」关系的展示形态未定。** 即便标注了弱关系，用户仍可能读成就业保证。这个问题可能不是数据建模能解决的，需要产品侧的表述设计介入（见[文档 03](03-产品需求文档-考生端.md)）。
4. **多省份 schema 扩展字段的治理成本未评估。** 接入 3 个省与接入 20 个省的维护成本差异是数量级的，当前没有任何量化。
5. **PKG 的规模上限未测。** 长期交互记忆积累一年后，单用户 PKG 的节点数是多少、检索性能如何，完全未知。这是一个需要在 Phase 2 之前验证的工程风险。
6. **EKG 批次更新的延迟与用户预期冲突。** 见 §9.2 的取舍，用户看到「数据截至某批次」时的反应未验证。
