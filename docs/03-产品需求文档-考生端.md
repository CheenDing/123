## 1. 本文的约定

**本文回答一个问题：考生端到底要做哪些功能，每个功能做到什么程度算「做完了」。** 因此本文不讨论技术选型（见[技术架构设计](05-技术架构设计.md)），只讨论行为、输入输出与判定标准。

### 1.1 需求编号规则

- `FR-C-M1-01`：功能需求，`C` 表示考生端，`M1`–`M4` 对应四个模块。
- `AC-xx`：验收口径，见 §11。
- 状态标记沿用规范 §3.3，**未标记者默认 `[规划]`**。

### 1.2 三个不可让步的设计前提 `[已确定]`

1. **理解人优先于匹配**：任何推荐都必须能回答「为什么是你」，不能只给分档结果。
2. **证据优先于结论**：画像条目的最小单位是「判断 + 证据 + 时间 + 置信度」，不是一句形容词。
3. **规则交给程序，解释交给模型**：选科、体检、单科要求等硬性约束由确定性规则引擎校验，LLM 不参与计算。

## 2. 产品目标与非目标

### 2.1 目标

| 编号 | 目标 | 状态 |
| --- | --- | --- |
| G1 | 让考生在填报之前完成一次**可沉淀**的自我探索，而不是出分后才开始想 | `[已确定]` |
| G2 | 把专业信息翻译成「学什么、怎么学、适合谁」，让考生具备基本判断力 | `[已确定]` |
| G3 | 输出可解释、可追溯、硬性规则零出错的志愿方案 | `[已确定]` |
| G4 | 让考生随时能看清「系统认为我是谁」，并能纠正它 | `[已确定]` |

### 2.2 非目标（明确不做）

| 编号 | 不做 | 理由 |
| --- | --- | --- |
| N1 | 题库、刷题、提分课程 | 与「认识自己」无关，且是红海 |
| N2 | 录取概率百分数 | 见 [用户研究与需求分析](02-用户研究与需求分析.md) §8.2，虚假确定感 |
| N3 | 心理诊断、人格标签、能力评分 | 触碰规范 §1.4 红线；且标签会反向限制考生 |
| N4 | 一键代填、代提交志愿表 | 决策权必须留在考生手里，产品只做「帮你想清楚」 |
| N5 | 考生社交社区、经验分享广场 | 内容治理成本高，且会引入无法溯源的二手信息 |
| N6 | Phase 1 覆盖全部省份 | 数据接入是硬约束，首期只做可核实口径的省份 `[假设]` |

## 3. 用户与冷启动

用户处境、三层信息不对称、家庭决策张力见 [用户研究与需求分析](02-用户研究与需求分析.md) 第 2、3、5 章，此处只补充一个工程性问题。

**冷启动问题：** 长期交互记忆的价值随时间增长，但新用户第一天没有证据。此时展示画像只能靠模型猜测，违反「无证据不生成」原则。

**处理方案 `[设计中]`：** 前 3 次会话只做「采集 + 复述」，不出结论；画像页显示空状态与采集进度。宁可空白，不可编造。

## 4. 核心用户旅程

### 4.1 端到端流程

```text
  高二暑假 ─────────── 高三上学期 ─────────── 出分前 ──────── 出分后 3–7 天
      |                    |                     |                  |
 +----v-----+       +------v------+       +------v------+    +------v------+
 | 冷启动    |       | 自我探索     |       | 专业发现     |    | 志愿决策     |
 | 采集与复述| --->  | 对话/练习    | --->  | 一页纸/匹配  | -> | 约束+方案    |
 +----------+       +------+------+       +------+------+    +------+------+
                           |                     |                  |
                    +------v---------------------v------+   +-------v------+
                    |       个人长期记忆与画像（贯穿）    |   | 方案解释与导出|
                    +-----------------------------------+   +--------------+
                                    ^                              |
                                    +---------- 反馈回流 -----------+
```

**关键点：** 画像不是独立页面，而是贯穿全流程的**底层能力**；决策阶段的每一次「接受 / 忽略 / 反驳」都会回流为新的证据。

### 4.2 各阶段的系统介入点

| 阶段 | 用户真实动作 | 系统介入 | 主要风险 |
| --- | --- | --- | --- |
| 冷启动 | 半信半疑地试用 | 只采集、只复述，快速给一次「你刚才说的我记下了」的正反馈 | 用户觉得没价值而流失 |
| 自我探索 | 断断续续，常中断 | 低负担任务、可随时暂停、下次接着聊 | 变成负担后被放弃 |
| 专业发现 | 密集搜索、比较 | 把搜索结果替换为结构化的「专业一页纸」 | 内容不准确导致误导 |
| 志愿决策 | 高压、时间极短 | 硬性规则校验 + 冲稳保 + 逐条解释 | 数据过期、规则漏判 |
| 反馈回流 | 事后复盘 | 记录对推荐的反应，作为新证据 | 用户不愿再回来 |

## 5. 模块一：个人长期记忆与个人画像

### 5.1 模块职责与边界

**负责：** 保存证据、维护画像条目、计算置信度、对外提供读写接口、执行用户的纠正与删除。
**不负责：** 生成话术、做推荐、做规则校验（分别属于其他模块）。

**与架构的对应：** 实现上「长期记忆」与「个人画像」分属两条写入路径——记忆是原材料（一段对话、一次记录），画像是基于原材料做出的带置信度的判断；二者共用存储但生命周期不同，见[技术架构设计](05-技术架构设计.md#33-模块边界与职责矩阵)。删除一条证据与撤销一个结论是两件独立的事。

### 5.2 证据的四个入口

| 入口 | 说明 | 状态 |
| --- | --- | --- |
| 探索对话 | 用户在苏格拉底式访谈中的原话 | `[已确定]` |
| 结构化任务 | Good Time Journal 记录、清单选择、路径草稿 | `[已确定]` |
| 用户主动录入 | 日记、随手记、对某专业的评论 | `[设计中]` |
| 第三方 AI 对话导入 | 用户授权后导入其与第三方 AI 的历史对话 | `[规划]`（默认关闭，须单独授权，见[数据治理隐私与合规](08-数据治理隐私与合规.md)） |

### 5.3 画像条目的数据结构

| 字段 | 说明 | 约束 |
| --- | --- | --- |
| `entry_id` | 条目唯一标识 | 不可复用；实体定义以[知识与数据建模](07-知识与数据建模.md#31-实体与节点类型)为准 |
| `topic` | 所属主题（兴趣 / 能力线索 / 价值观 / 约束条件） | 主题体系见[知识与数据建模](07-知识与数据建模.md) |
| `claim` | 一句话判断，如「对空间与改造类任务有兴趣」 | 必须可被证据支持或反驳 |
| `evidence_refs` | 证据 ID 列表，每条含原文定位与时间 | **至少 1 条**，否则不生成 |
| `confidence` | 低 / 中 / 高 | 分档口径由[知识与数据建模](07-知识与数据建模.md)定义 |
| `first_seen` / `last_seen` | 首次与最近一次被证据支持的时间 | 用于时效衰减 |
| `derived_from` | 该条目由哪些上游条目 / 证据派生 | 用于用户纠正后的级联失效，见 §5.4 第 6 条 |
| `reviewed_at` | 用户最近一次确认、纠正或否认的时间 | 用于过期降档判定，口径见[数据治理隐私与合规](08-数据治理隐私与合规.md#51-字段约定与治理约束) |
| `status` | 待验证 / 验证中 / 已确认 / 已否决 / 存在矛盾 / 衰减归档 | 取值以[知识与数据建模](07-知识与数据建模.md#32-验证状态机)为准，见 §9.2 |
| `visibility` | 私有 / 可分享给家庭 / 可授权给高校 | 默认私有 |

> 命名说明：实体与字段名以[知识与数据建模](07-知识与数据建模.md#31-实体与节点类型)为准（条目用 `entry_id`，状态用 §9.2 的六态）。收口阶段已校正全文档的早期同义异名，当前 03 / 07 / 08 三处口径一致；若后续再出现异名，以文档 07 为基准修订。

### 5.4 证据链的六条硬规则 `[已确定]`

这六条是产品伦理的核心，不是附录条款，因此直接写进需求并作为验收项：

1. **无证据不生成**：任何画像条目必须至少关联 1 条原始证据，否则不得写入、不得展示。
2. **证据不可改写**：原始片段只允许「失效」（标记为不再采纳），不允许编辑内容；编辑会破坏可追溯性。
3. **时间可见**：每条条目展示首次与最近支持时间；超过一定时长未被新证据支持时，置信度自动降档（阈值由[知识与数据建模](07-知识与数据建模.md#33-置信度分档定义)定义）。
4. **可查看、可纠正、可删除**：用户对任一条件拥有查看证据原文、修改判断表述、删除条目三项权利。
5. **否认即负证据**：用户否认的条目进入「已否决」并不再复用；否认原因作为负证据保留，用于抑制模型在同类证据上重复得出同一错误结论。
6. **纠正即级联**：用户纠正或删除某条目时，所有 `derived_from` 指向它的下游条目必须级联失效或自动降档，并在界面上告知用户「以下 N 条相关判断已同步更新」；**不允许出现「上游已被否认、下游仍以高中置信度展示」的状态**。

> 第 6 条是与[数据治理隐私与合规](08-数据治理隐私与合规.md#51-字段约定与治理约束) §5.1「纠正必须级联」对齐的接口约束：`derived_from` 与 `reviewed_at` 两个治理字段的定义权在文档 08，本文只约定 03 侧的行为与界面义务。两侧若再调整字段语义，须同步修改本节。

### 5.5 交互要点（画像条目详情页）

```text
+--------------------------------------------------------------+
| 个人画像 > 兴趣主题 > 「对空间与改造类任务有兴趣」            |
+--------------------------------------------------------------+
| 置信度：中   状态：已确认   首次：2026-09-18  最近：2026-09-25 |
|                                                              |
| 支撑证据（2 条）                                              |
|  +--------------------------------------------------------+  |
|  | E-1042  2026-09-18  探索对话                           |  |
|  | 「如果不用考虑钱，你会先改造老房子的哪里？」            |  |
|  | 你的回答：……                              [查看原文]   |  |
|  +--------------------------------------------------------+  |
|  | E-1107  2026-09-25  Good Time Journal                  |  |
|  +--------------------------------------------------------+  |
|                                                              |
| [这条判断不对]   [修改表述]   [删除这条判断]                  |
| 提示：删除后该条判断立即停止展示，其派生条目按级联规则        |
|       同步失效；底层数据的留存与彻底删除遵循文档 08 §3.5      |
+--------------------------------------------------------------+
```

**交互要点：**
- 证据原文只读，长文本可展开；不做截断式摘要代替原文。
- 「这条判断不对」必须让用户选择原因（证据理解错 / 我变了 / 不适合描述我），原因进入负证据。
- 删除为软删除，用户可在「回收站」内恢复（保留期由[数据治理隐私与合规](08-数据治理隐私与合规.md)规定）。

### 5.6 边界与异常

| 场景 | 处理 |
| --- | --- |
| 新旧证据互相矛盾 | 条目进入「存在矛盾」，并列展示两组证据，不自动取新弃旧；提示用户裁决 |
| 支撑证据被用户删除 | 条目退回「待验证」；若无剩余证据则条目不展示，但保留记录 |
| 长期无新证据 | 置信度按时间衰减降档；不自动删除 |
| 导入解析失败 | 展示失败原因与可重试范围，不写入任何不完整证据 |
| 用户删除后同类判断再次出现 | 负证据抑制窗口内不自动生成，需用户主动确认 |
| 未成年人授权 | 首次使用需监护人知情确认流程，详见[数据治理隐私与合规](08-数据治理隐私与合规.md) |

## 6. 模块二：人生设计与自我探索

### 6.1 方法论到产品形态的映射

| 方法论 | 产品形态 | 频率 | 状态 |
| --- | --- | --- | --- |
| Workview / Lifeview | 两次结构化访谈，各约 15 分钟，产出一段用户自己的表述 | 一次性，可重做 | `[设计中]` |
| Good Time Journal | 轻量记录：每天 1 个问题、1 分钟，周末回看 | 周周期 | `[设计中]` |
| Odyssey Plans | 三条五年路径草稿（延续当前 / 转向 / 无约束版） | 一次性 | `[设计中]` |
| 苏格拉底式访谈 | 由 Coach Agent 主导的追问式对话，贯穿以上三项 | 常驻 | `[已确定]` |

**取舍：** 不做标准化量表打分。量表给的是与他人比较的分数，而本模块要回答的是「你怎么描述你自己」——一旦引入比较，叙述就会退化为对号入座。

### 6.2 Coach Agent 的行为规范

| 编号 | 规范 | 说明 |
| --- | --- | --- |
| B1 | 一次只问一个问题 | 多问会诱发用户挑简单的答 |
| B2 | 不预设答案、不给选项诱导 | 「你是不是更喜欢动手？」属于引导性提问，禁止 |
| B3 | 不评价、不判断好坏 | 「这个想法很好」会污染后续回答 |
| B4 | 任何问题可跳过，跳过不追问 | 尊重边界，也避免逼出虚假回答 |
| B5 | 每轮有明确目标并说明 | 让用户知道「这轮在拆什么」 |
| B6 | 收敛条件明确 | 每轮结束须产出 0–3 条待确认画像条目，或明确「本轮无产出」 |

### 6.3 交互要点（探索对话页）

```text
+---------------------------------------------------+
| 个人 Agent                             [暂停探索] |
+---------------------------------------------------+
| 本轮目标：把「喜欢动手」拆成可验证的具体场景       |
|                                                   |
| Coach：上次你提到，做模型的时候时间过得很快。      |
|        如果让你连续做四小时不觉得累，会是什么事？  |
|                                                   |
| [自由回答]        [换个问法]        [跳过这题]     |
+---------------------------------------------------+
| 本轮将写入画像：0 条（需你确认）      [查看待确认] |
+---------------------------------------------------+
```

**要点：** 对话页始终显示「本轮目标」与「将写入什么」，让用户对系统的推断保持知情。

### 6.4 边界与异常

| 场景 | 处理 |
| --- | --- |
| 用户连续敷衍（「都行」「不知道」） | 连续 3 次后切换问法（从抽象问题改为具体场景题），或建议暂停 |
| 用户表达强烈负面情绪 | 不进入探索流程，提供退出与求助指引；不做任何心理判断 |
| 用户要求「直接告诉我适合什么」 | 拒绝直接给结论，改为提供「基于现有 5 条证据的倾向排序 + 每条的依据」 |
| 对话轮次过长 | 单次会话超过设定轮次上限即提示分段，避免疲劳 |
| 用户要求删除整段对话 | 连带删除由其产生的证据与条目，并记录删除操作日志 |

### 6.5 验收口径

见 §11 的 `AC-04`。

## 7. 模块三：专业发现

### 7.1 「专业一页纸」

每个专业（按高校粒度，而非学科粒度）呈现一页结构化信息：

| 区块 | 内容 | 来源要求 |
| --- | --- | --- |
| 培养目标 | 该专业培养什么人 | 培养方案，须标注年份 |
| 课程结构 | 通识 / 学科基础 / 专业核心 / 实践环节，各举代表课程 | 培养方案 |
| 能力要求 | 学习该专业需要的能力与先修知识 | 培养方案 + 院系提供 |
| 典型学习体验 | 一周大概在做什么（实验、设计、阅读、编程） | 院系或在校生提供，须标注来源等级 |
| 常见误解 | 该专业最容易被望文生义的地方 | 编辑整理，须标注依据 |
| 升学与转向 | 考研方向、转专业政策、辅修可能 | 官方政策文本，须标注年份 |

**数据缺失时：** 相应区块显示「暂无公开数据」，不得用模型生成内容填充。

### 7.2 兴趣主题到专业的映射路径

```text
  画像条目（证据化）        学科知识点            专业培养要求
  「对空间改造有兴趣」 ---> 设计基础/建筑制图 ---> 建筑类专业的核心课程
        |                        |                        |
        +--- 反向验证 -----------+--- 专业一页纸 ---------+
                    |                                    |
                    v                                    v
             匹配解释卡：为什么推荐给你 + 不确定在哪
```

**说明：** 映射不靠关键词相似度直接连线，而是经过「学科知识点」这一中间层，目的是让解释可核查——用户能看到「哪条证据 → 哪个知识点 → 哪门课」的完整链条。图谱设计见[知识与数据建模](07-知识与数据建模.md)。

### 7.3 三条探索路径

| 路径 | 入口 | 适用 |
| --- | --- | --- |
| 正向 | 从画像出发，看可能相关的专业方向 | 已有一些探索积累 |
| 反向 | 从某个感兴趣的专业出发，回看它要求什么、我是否具备 | 被某个专业吸引 |
| 倒推 | 从想做的职业或生活状态倒推专业与路径 | 目标清晰但路径不清 |

### 7.4 匹配解释卡

每条推荐必须包含四项，缺一不可：

1. **依据**：关联的画像条目及其证据（可点开查看）。
2. **映射**：从证据到学科知识点到专业培养要求的链条。
3. **不确定性**：这条推荐最可能错在哪里（例如「仅基于 1 条证据」「该专业在不同高校差异大」）。
4. **反向信息**：这个专业有哪些可能不适合你的地方。

### 7.5 边界与异常

| 场景 | 处理 |
| --- | --- |
| 培养方案缺失或过期 | 显示口径与年份，标注「仅供参考」，不参与强推荐 |
| 专业更名、合并、停招 | 以教育部专业目录与高校最新招生专业为准，保留历史名称的映射说明 |
| 同名专业跨校差异大 | 强制按高校粒度展示，禁止跨校合并为一条「专业介绍」 |
| 用户对推荐强烈反驳 | 记录为负证据，并即时调整该主题下的推荐排序 |
| 用户只看热门专业 | 不阻断，但在一页纸中固定展示「常见误解」区块 |

**取舍：** 我们不做「专业热度榜」。热度是结果而不是原因，且会自我强化；我们改为在专业页展示招生计划的变化趋势（如有可靠数据），并明确标注口径。

## 8. 模块四：智能志愿决策

### 8.1 立场：决策不等于匹配

匹配问题问「哪些选项符合条件」，决策问题问「在这些选项里，我愿意承担哪种风险」。前者可以算，后者必须由考生自己答。产品的职责是把决策所需的信息与后果讲清楚，而不是替他决定。

### 8.2 输入

| 输入项 | 必填 | 说明 |
| --- | --- | --- |
| 省份 / 年份 / 批次 / 科类或选科 | 是 | 决定规则集与数据口径 |
| 分数与位次 | 是 | 位次为主，分数仅作参考 |
| 体检结论与受限项 | 否 | 影响专业受限判断 |
| 家庭约束（学费上限、地域限制等） | 否 | 用户可拒绝填写 |
| 偏好权重（专业契合 / 城市 / 院校层次 / 学费） | 否 | 默认为均等，可拖动调整 |
| 已确认的画像条目 | 自动带入 | 用户可逐条排除 |

### 8.3 LLM 与确定性规则引擎的分工

| 事项 | 执行者 | 理由 |
| --- | --- | --- |
| 选科要求、单科成绩要求、体检受限、批次与投档规则校验 | 确定性规则引擎 | 可由规则精确判定，不允许概率性输出 |
| 招生计划与往年录取数据的口径比对 | 确定性规则引擎 | 纯数据计算 |
| 冲稳保分档的位次区间计算 | 确定性规则引擎 | 可复算、可审计 |
| 专业与画像的契合度解释 | LLM | 需要语义理解与自然语言组织 |
| 风险叙述与取舍说明 | LLM（受规则结果约束） | 需要把结构化结果翻译成人话 |
| 任何数值结论 | **不得由 LLM 生成** | 防幻觉，且必须可复算 |

### 8.4 输出

- **三档方案**：冲（Reach）、稳（Match）、保（Safety），每档给出条目数与排序逻辑说明。
- **每条志愿的解释**：契合依据、硬性校验结果（通过 / 不通过 / 缺数据）、风险点、数据口径与年份。
- **全局风险提示**：数据缺口、计划波动、专业组内调剂风险等。
- **不确定性声明**：明确写出「本方案不构成录取承诺」。

### 8.5 交互要点（志愿方案页）

```text
+------------------------------------------------------------+
| 志愿方案 v3    省份：示例省  科类：示例  位次：示例（示意）  |
+------------------------------------------------------------+
| 权重：专业契合 ●●●●○  城市 ●●○○○  院校层次 ●●●○○  学费 ●○○○○ |
|                               [重算并解释变化]              |
+------------------------------------------------------------+
| 冲 (Reach) 2 条   稳 (Match) 3 条   保 (Safety) 2 条        |
| +--------------------------------------------------------+ |
| | 01 | 示例大学 A | 示例专业组 1 | 契合：高 | 硬性校验：通过 | |
| |    | 依据：E-1042 / E-1107                              | |
| |    | 风险：该专业组招生计划近两年波动较大（示例数据）    | |
| +--------------------------------------------------------+ |
| 数据口径：示例省 20XX–20XX 年投档数据，来源：示例          |
| [导出志愿表]   [对这条提异议]   [查看完整数据口径]          |
+------------------------------------------------------------+
```

**交互要点：**
- 权重调整后不静默重排，而是先展示「哪些条目进出、原因是什么」，让用户理解变化。
- 每条志愿的「硬性校验」必须可展开查看命中了哪条规则、规则来自哪份文本。
- 「提异议」进入负证据，影响后续契合度解释。

### 8.6 边界与异常

| 场景 | 处理 |
| --- | --- |
| 出分前使用 | 不输出分档，只做「专业方向预演」与约束清单 |
| 某省某年数据缺失 | 明确标注缺失范围，相应条目降级为「信息不足，需自行核实」 |
| 招生计划较往年变动大 | 提示波动，不给出确定结论 |
| 体检受限命中 | 直接过滤或强提示，不允许用户以「我知道」跳过（可显示但置灰） |
| 无可行方案（条件互斥） | 如实说明冲突项，给出「放宽哪个条件可以解」的选项，不硬凑方案 |
| 用户拒绝填写偏好 | 退化为纯约束过滤，明确告知「本方案未考虑你的偏好」 |

## 11. 验收口径汇总

验收只看**可核查的过程质量**，不看效果承诺（不承诺提高录取率）。

| 编号 | 指标 | 口径 | 判定方式 |
| --- | --- | --- | --- |
| AC-01 | 画像条目证据覆盖率 | 展示的条目中关联 ≥1 条证据的比例 = 100% | 抽样审查 + 自动检查 |
| AC-02 | 用户可控性 | 查看 / 纠正 / 删除三项操作均可用且生效 | 功能测试用例全覆盖 |
| AC-03 | 纠正与级联留痕 | 每次纠正均产生负证据记录；下游 `derived_from` 派生条目同步失效或降档，且界面有「已同步更新」告知 | 数据抽查 + 界面走查 |
| AC-04 | 探索产出率 | 每轮对话产出 0–3 条待验证条目，且用户确认前不入正式画像 | 对话日志审查 |
| AC-05 | 硬性规则零漏判 | 对给定测试集，选科 / 体检 / 单科要求的校验结果与人工标注一致率 100% | 规则回归测试集 |
| AC-06 | 结论可溯源 | 方案中每条解释性语句均可指向规则结果或证据 ID | 人工评审抽样 |
| AC-07 | 数据口径完整 | 每条录取相关数据均带省份、年份、科类、批次、来源五项 | 字段校验 |
| AC-08 | 无录取承诺表述 | 全站文案中不含概率百分数与结果承诺 | 文案审查清单 |

## 12. 取舍与开放问题

### 12.1 取舍一：不做「一键生成整张志愿表」

**放弃什么：** 用户填完分数点一下，直接输出一张可提交的志愿表。

**为什么：** 其一，这会把产品的价值压缩成「算得快」，而责任仍在用户身上，一旦出问题无法解释；其二，志愿表的排序偏好是高度个人化的，模型无法替用户决定「我更怕滑档还是更怕浪费分」；其三，这会让我们滑向 N4（代填）的红线。

**替代：** 输出「方案 + 每条的依据 + 可调整的权重」，并支持导出为待填表格，由用户自己完成最终排序与提交。

### 12.2 取舍二：Phase 1 只做少数省份

**放弃什么：** 首期不做全国覆盖。

**为什么：** 新高考规则按省份差异极大，数据口径与规则集需逐省核对；覆盖过宽会形成「看起来能用、实际错漏」的状态，比明确不覆盖更危险。代价是初期可用人群受限，这不靠产品手段解决，只能靠数据接入推进（见[路线图与里程碑](10-路线图与里程碑.md)）。
