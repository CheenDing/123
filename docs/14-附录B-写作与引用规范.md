## 1. 项目事实基线（写作前必须接受的前提）

这套文档服务的是一个**早期研发阶段**的项目。所有文字都必须与下列事实一致，不得为了「看起来更完整」而虚构。

### 1.1 允许陈述为「已确定」的内容

- 项目名称、核心理念、三条基本原则（Understand the Person / Explore the Possibilities / Make Informed Decisions）。
- 两个产品方向：Personal Education Discovery（面向考生）、University Intelligence（面向高校）。
- 四个阶段的产品路线（Phase 1–4）及其主题划分。
- 模块划分与职责边界（Personal Memory / Self Discovery / Major Discovery / University Agent / Admission Agent / Decision Engine / Knowledge Graph / Data Governance）。
- 技术方向的**候选集**（LLM & Agent、Agent Skills & Tool Calling、RAG & Hybrid Retrieval、Long-term Memory、Knowledge Graph、Multi-objective Optimization、Structured Decision Making、Data Engineering）。
- 五个核心研究问题。
- 东北大学作为**试点场景的合作意向与设想**。

### 1.2 只能以「规划 / 设计 / 假设」措辞出现的内容

| 禁止写法 | 必须改写为 |
| --- | --- |
| 系统已支持导入 ChatGPT 对话 | 系统**将**支持／**规划**支持导入第三方 AI 对话记录 |
| 我们的录取预测准确率 95% | 我们**设定**录取风险提示的目标为……（并给出可验证的验收口径） |
| 东北大学官方招生 Agent 已上线 | 东北大学招生 Agent 为**试点建设目标**，非校方官方服务 |
| 已建成覆盖 30 省的数据 | **计划**分阶段接入多省份招生数据，Phase 3 为首批目标 |
| 用户量 / 合作高校数量 | 一律不写具体数字，除非有可溯源来源 |

### 1.3 绝对禁止

1. **不虚构数据**：任何录取分数、位次、招生计划、专业课程门数、师资人数、就业率，一律不得凭空写出具体数值。
   - 需要举例时，写「示例数值（仅用于说明计算口径，非真实数据）」并明显标注。
2. **不虚构官方身份**：不得暗示本项目是高校、考试院或任何政府机构的官方系统。
3. **不虚构合作**：除东北大学试点**意向**外，不得写出任何具体合作单位名称、LOGO、协议状态。
4. **不做效果承诺**：不得承诺「提高录取率」「保证匹配准确」等结果性表述；只能承诺**方法与可验证性**。
5. **不复制他方文案**：不得整段引用第三方产品介绍、论文摘要；引用需按 §5 规范标注。

### 1.4 合规红线（与文档 08 呼应）

- 涉及未成年人/高中生个人数据：默认「最小必要 + 明示授权 + 可撤回 + 可删除」。
- 第三方 AI 对话记录属于**用户本人的个人数据**，导入必须基于用户主动授权，且需说明处理范围与留存期限。
- 任何画像结论必须可追溯到原始证据（evidence）、时间戳与置信度，并允许用户查看、纠正、删除。
- 不得输出「心理诊断」「人格障碍」「录取保证」类表述。

## 3. 文档结构规范

### 3.1 每篇文档必须以信息表开头

```markdown
| 项目 | 内容 |
| --- | --- |
| 文档编号 | NN |
| 文档类型 | 愿景 / 需求 / 设计 / 规范 / 计划 / 评估 |
| 目标读者 | …… |
| 版本 | v1.0 |
| 状态 | 草稿 / 评审中 / 生效 |
| 上游依赖 | 文档 NN（标题） |
| 下游影响 | 文档 NN（标题） |
```

### 3.2 章节编号

- 一级标题用 `## 1. xxx`、`## 2. xxx`；二级 `### 1.1`；最多到三级 `#### 1.1.1`。
- 文档主标题用 `#`，且只出现一次。
- 不跳级：不允许 1 → 1.2。

### 3.3 状态标记（正文内联）

对具体功能/能力，用行内标记区分成熟度：

- `[已确定]` — 属于项目既定理念或架构约定，不会随实现改变。
- `[设计中]` — 已有方案但仍在演进。
- `[规划]` — 路线图内，尚未设计细节。
- `[研究]` — 属于开放研究问题，结论未定。
- `[假设]` — 明确标注为待验证的假设，必须写验证方式。

**任何功能描述如果没有标记，默认视为 `[规划]`。**

### 3.4 表格与图示

- 表格必须有表头，列数不超过 6 列。
- 图示优先用 ASCII 框图（保证任何 Markdown 阅读器可读）；Mermaid 仅作为补充，且必须同时给出 ASCII 版本。
- 关键架构图统一使用以下风格（文档 05 会给出完整版）：

```text
  +-------------------+
  |   Component Name  |
  +---------+---------+
            |
            v
  +-------------------+
```

### 3.5 篇幅目标

| 文档类型 | 建议字数（中文字符） |
| --- | --- |
| 愿景 / 导读 | 1,500 – 2,500 |
| 需求 / PRD | 3,000 – 5,000 |
| 架构 / 设计 | 3,500 – 6,000 |
| 规范 / 治理 | 2,500 – 4,000 |
| 计划 / 评估 | 2,000 – 3,500 |
| 附录 | 1,000 – 2,500 |

宁可写透一个章节，也不要为凑字数灌水。**空洞的正确话是这篇文档最大的失败。**

## 4. 写作风格

1. **先结论，后论证。** 每节第一段给出该节要回答的问题与简明答案，再展开。
2. **面向读者写作。** 假设读者是：评审老师、潜在合作高校招生办、可能的队友。他们不熟悉你的内部黑话。
3. **敢写取舍。** 每个设计章节至少给出 1 个「我们放弃了什么、为什么」。没有取舍的设计文档不可信。
4. **区分「用户价值」与「技术炫技」。** 先讲用户能得到什么，再讲用了什么技术。
5. **不用形容词堆砌。** 禁止「赋能、闭环、抓手、颗粒度、打法」这类词；「赋能」在原始愿景中出现过，可在愿景文档保留一处，其余文档禁用。
6. **数字要有单位与口径。** 「响应时间 < 3s（P95，单轮对话首字返回）」而不是「响应很快」。
7. **中英文之间加空格**：`使用 LLM 生成` 而非 `使用LLM生成`。
8. **标点用中文全角**，代码、路径、字段名用反引号。

## 5. 引用与链接规范

### 5.1 内部交叉引用

- 使用相对路径 + 中文锚点，例如：
  `详见 [技术架构设计](05-技术架构设计.md#3-多智能体编排)`
- 文档编号引用可用纯文本：`见文档 07 第 4 节`。
- **不得**引用尚不存在的章节号；如果依赖方还没写，写「见文档 NN（待补）」。

### 5.2 外部引用

- 方法论引用（如 Designing Your Life）、政策文件（如各省新高考改革方案）、标准（如个人信息保护相关法规）必须给出可核查来源。
- 格式：`作者/机构. 标题. 年份. <链接>`，链接用 Markdown 行内链接。
- 无法给出来源的信息，降级为 `[假设]` 或删除，**不要留「据说」「业内认为」**。

### 5.3 数据口径引用

引用任何招生/录取数据时，必须同时写明：省份、年份、科类/选科、批次、数据来源。缺一项即视为不可用。
